## 0. 前提と置いた仮定

- 起点は main に #397〜#399 が入り、その上に #400（JPEG の経路、固定の合成条件 v1、倍率の補正）と #401（ライブの C）が積まれた状態。#400・#401 は統合前なので、この文書は v1 の設計を変えず、別の文書として足す
- v2 の元になる校正は、#374 の平置き校正が書く rig profile 2.0.0 の draft（校正の値あり、所有者の決定の欄は null）。#374 の内部パラメータは公称の K で、主点は画素の格子の中心 ((w−1)/2, (h−1)/2) に置かれる（`NominalIntrinsics`）。#374 の文書座標は重なりのチャートの座標（`OverlapChartPlacement` で用紙に置き直せる）
- 非機能の目標（※仮定）: JPEG の合成は、両台撮影の 180 秒の期限の中で、原画像の保存とゲート（校正済みの写像で約 40 秒、[品質ゲート](../M2_SEAM_QUALITY_GATE.md) の 16.9 節）の残りに収める。C は ADR-0036 決定1 の 9 の見込み（1 枚 35〜65 ms、※推定）を超えないことを目標にする。どちらも実装の前後に開発用の PC で測る（実機は使わない）
- データ整合: 固定の合成条件は不変の記録で、作り直す時は新しい記録にする（ADR-0037 の不変条件3）。1 回の撮影の中で「条件を読む → 写像を作る → 倍率を決める → 合成 → ゲート → 報告」が閉じ、報告は使った条件と profile の hash を持つ。条件を複数のプロセスが書き換えることは無い
- 背景の実測: 保存済みの平置きチャートの組を、歪みを含む校正（val02）で合成すると、継ぎ目の中ほどのずれは小さく、上下の両端だけが大きい。相似だけで合成すると端はさらに大きい。今の JPEG（#400）は v1 の相似だけで合成し、歪みを補正しない。値は非公開の基準セットにある

## 1. 目的

v1 の写像は B を A に重ねる相似（平行移動・回転・倍率）だけで、レンズの歪みを表せない。継ぎ目は A の右端と B の左端、どちらもレンズの縁を通るので、歪みの差がいちばん大きく出る所に置かれている。v2 は、校正（#374）が求めた「文書の面 → 各カメラの生画素」の写像（内部パラメータ、Brown–Conrady の 5 係数、文書→画像の射影）で合成し、JPEG と C の両方をその写像で描く。

所有者の決定（#396）はそのまま守る。

- C と JPEG は同じ固定の合成を使う。写像は撮影ごとに変えない
- 継ぎ目は縦 1 本の列。人が C で線をドラッグして決める（#403）
- 明るさの比は撮影ごと（C は frame ごと）に求める
- 倍率だけは、左右の差が上限（1% から始める）以内なら撮影ごとに補正する。回転と平行移動は固定。中心は B の画像の中心を固定の写像で出力へ移した点。推定できない時は補正しない

v2 が直すのは「相似では表せない歪み」の分だけで、校正そのものの誤差（点の無い所の外挿）は残る。両端のずれが消えるには、画面の角と継ぎ目の上下の端まで点が写る校正のやり直し（10 節、H1）が要る。

## 2. 推奨案の要約

| 決めること | 推奨（※案） |

| v2 の写像の持ち方 | 校正の draft profile を参照する。条件は profile のファイルの SHA-256 と fingerprint を持ち、値は持たない。profile は条件と同じフォルダに内容の hash から作った名前で置く（3.2 節） |
| 出力の格子 | 条件が出力ラスタ（文書の µm の領域と整数の DPI）を持つ。所有者の決定ではなく開発用の未承認の値。倍率の上限の範囲のどの k でも覆えることを、作る時に確かめる（3.3 節） |
| v1 との並存 | ファイル名は v1 と同じ 1 つ。中の `schema` で v1 か v2 かを分け、v1 は今の関数、v2 は文書の写像で描く。両方を同時に置く形は作らない（3.8 節） |
| 合成の関数 | #398 の混ぜる部分（帯の標本化、明るさの比、継ぎ目に沿った合成）を「出力画素→生画素」の写像の対（`render::OutputToCamera`）で動くように一般化し、v1 と v2 で共有する。v1 の出力のバイト列は変えない。C と JPEG は同じ関数と同じ写像の作り手を通る（4 節） |

| 中心 P | B の画素の格子の中心 ((w−1)/2, (h−1)/2) を、B の固定の写像の逆（歪みを外し、文書→画像の逆）で文書へ移した点。#374 の profile では主点と一致し、歪みが 0 の点なので閉じた式で求まる（5.2 節） |
| 倍率の推定 | #400 の推定器が返す合意したタイルを使い、A と B の点をそれぞれ固定の写像の逆で文書の mm へ移してから、回転なし・平行移動は推定の中だけ自由で k を求める（5.3 節） |

| 作る入口 | StillReview の開発用 CLI に v2 の作り方を足す。人が profile、領域、DPI、設定のフォルダを明示して一度だけ作る（8 節） |

## 3. 固定の合成条件 v2 の中身

### 3.1 持つもの（書式 `a0.fixed-composite-condition.v2`、※案）

| 欄 | 単位・座標 | 備考 |
|---|---|---|
| `schema` | 文字列 | `a0.fixed-composite-condition.v2` |
| `approval` | 常に `unapproved` | v1 と同じ。承認を表す値は持てない |
| `createdUtc` | UTC（秒） | v1 と同じ |
| `revision.parentSha256` | 64 桁の小文字 16 進か null | 前の記録の SHA-256（ADR-0037 の不変条件3、#396 の A3）。最初の記録は null。どの記録を有効にするかは #403 で決める |
| `source.profileFile` | ファイル名 | 条件と同じフォルダにある draft profile の名前。フォルダの区切りを含まない |
| `source.profileFileSha256` | 64 桁の小文字 16 進 | profile のファイルのバイト列の SHA-256 |
| `source.profileFingerprintSha256` | 64 桁の小文字 16 進 | ADR-0034 の 6 の fingerprint（`RigProfileV2::FingerprintSha256`）。読む時に計算し直して照合する |
| `mountOrientation` | `normal` / `rotated-180` | 校正した時の取り付けの向き。今の向きと違えば使わない（3.7 節） |
| `outputRaster` | 文書の µm、整数の DPI、出力の画素 | `regionUm`（left・top・right・bottom）、`dpi`、`widthPixels`・`heightPixels`。`render::OutputRaster` と同じ形で、画素数は µm と DPI の切り上げと一致させる（ADR-0034 の 2） |
| `scaleAutoCorrectionMaxPercent` | % | v1 と同じ。作る時に方針ファイルから写す。コードの既定値にしない |
| `seam.column`・`seam.origin` | 出力ラスタの画素の列 | v1 と同じ意味。`origin` は `band-center-provisional` か `operator` |

持たないもの:

- 写像の値（内部パラメータ、係数、射影）: profile が持つ（3.2 節）
- 撮影画像の大きさ: profile の `cameraModel` が D810 の値に固定している
- 合成の補間の種類: v2 の合成関数の定数にする（bilinear、#398 と同じ）。条件の欄にすると、C と JPEG で違う値を渡せる口が増える
- 有効期限: v1 と同じく持たない（決まっていない）

### 3.2 校正の写像の持ち方: 参照か埋め込みか

| 観点 | A. profile を参照（推奨） | B. 値を条件に写す | C. profile の全文を条件の中に文字列で持つ |
|---|---|---|---|
| 開発速度 | `RigProfileV2::Parse` と `ValidateCalibrationForEvaluation`（校正済みの draft だけを受け、`DocumentRenderParameters` を返す）をそのまま使える。新しく書くのは参照と hash の照合だけ | 内部パラメータ・係数・行列の reader を条件の側にもう 1 つ書く | reader は流用できるが、文字列の中の JSON の取り出しと上限の拡張が要る |
| 運用コスト | ファイルが 2 つになる。片方が欠けた・違う時は「条件を使えない」に倒す。列の改訂（#403）では profile を写さない | 1 ファイルで済む。改訂のたびに校正の値も写る | 1 ファイル。改訂のたびに profile の全文が写り、条件が大きくなる（v1 の上限は 4 KiB、profile は最大 256 KiB） |
| スケーラビリティ | profile の版が上がっても条件の書式は変わらない（fingerprint で結ぶ） | profile の欄が増えるたびに条件の書式も上げる | 条件の書式は変わらない |
| 学習コスト | #356 の保存した評価条件が、同じく profile を SHA-256 で参照している | 校正の値が 2 か所にあり、どちらが正かを覚える必要がある | 人が条件を読んでも中身が見えない |
| 既存スタックとの親和性 | StitchEval と同じ profile のファイルを使うので、評価と開発経路を fingerprint で突き合わせられる | ADR-0034 の reader（未知の欄、重複キー、整数の表記の拒否）と別の reader ができ、検査がずれうる | reader は共有できる |

推奨は A。理由:

1. 校正の値の正本が profile の 1 か所に残る。ADR-0034 の reader と実行時の検査（`ValidateCameraProjection` の分母の符号、放射の単調性）を通った値だけが合成に入る
2. 列の改訂（#403）と再校正を分けられる。列を動かした改訂は同じ profile を指し、再校正は profile と条件の両方を新しくする
3. #356 の参照の作り（SHA-256 での照合）と、StitchEval の評価（同じ profile のファイル）を流用できる

B は「同じ値の 2 つ目の reader」を作ることになるので外した。C は reader を流用できる点は良いが、文字列の中の JSON は人が確かめられず、改訂のたびに大きな記録が増えるので外した。

A の作り（※案）:

- profile は条件と同じフォルダに、内容の SHA-256 の先頭から作った名前（例 `wpd-fixed-composite-profile-<16 桁>.json`）で置く。作る入口（8 節）が指定された profile を写す。同じ名前で同じバイト列なら写さずに使う。違うバイト列なら拒否する（上書きしない）
- 読む側は、条件の `source.profileFile` を同じフォルダの中だけで探す。区切り、親のフォルダ、別のドライブを含む名前は拒否する。バイト列の SHA-256 と fingerprint の両方を照合し、どちらかが違えば「条件を使えない」にする
- profile は校正済みの draft だけを受け付ける。approved の profile は製品の経路が使うもので、開発経路の未承認の条件に混ぜない（`ValidateCalibrationForEvaluation` が approved を拒む）。`documentPlane.cameraOrder` は `CAM-A-left-CAM-B-right` だけ（#398 の合成は A 左・B 右だけ）

### 3.3 出力ラスタ

- 出力は文書の面の格子で、出力画素 (i, j) は文書の点 (left + (i+0.5)·p, top + (j+0.5)·p)、p = 25.4/DPI mm（ADR-0034 の 2、`DocumentOutputToCamera` と同じ算術）
- 領域と DPI は所有者の決定（`HG-0001`）として profile には置かない（ADR-0034 の 4・5）。v2 の条件が持つのは、#273 の評価 exe と #356 の保存した評価条件と同じく、開発用に人が指定した未承認の値。所有者の決定として扱わず、記録と画面に未承認と出す
- **出力の大きさを撮影ごとに変えない**（※案）。v1 は倍率を当てると覆える窓を計算し直し、出力の右端と上下が撮影ごとに少し変わる（`FixedCompositeScaledGeometry`）。v2 の出力は文書の mm で決めた格子なので、撮影ごとに変えると「文書の同じ範囲を同じ DPI で出す」という ADR-0034 の出力の考え方から外れる。そこで作る時に、倍率の上限の範囲の両端 k = 1 ± 上限/100 と k = 1 のすべてで、出力のすべての標本が A か B に覆われ、継ぎ目の列と混ぜ幅の半分がすべての行で A と B の両方に入ることを確かめる。P を中心にした拡大では、B の写る範囲が P から見て星形（P から出た半直線が枠を 1 回だけ横切る）なら、k が小さいほど B の写る範囲は小さくなり、小さい側の端で覆えれば間の k も覆える。歪みが単調（ADR-0034 の実行時の検査）で射影の分母が正なら成り立つ見込みだが（※推定）、念のため両端と 1 の 3 通りを確かめる
- DPI の選び方は所有者に確認する（15 節の 4）。ゲートの合格線 1 px は書き出す画像の画素で数える（#385 Q2）ので、DPI を下げるとゲートの 1 px が文書の上で長くなる。v1 の JPEG は撮影画像の画素とほぼ同じ細かさなので、v1 と比べるには撮影画像と同じ程度の細かさ（継ぎ目のあたりで 1 出力画素 ≒ 1 撮影画素）が合う。この DPI は写像から計算して入口が表示する（8 節）。値は人が指定する
- 混ぜ幅と明るさの窓（`kSeamBlendDesign`）は #398 と同じく出力の画素で数える。DPI を撮影画像と同じ程度にすれば、v1 と同じ長さを混ぜることになる。DPI を大きく変える時に定数を換算するかは、その時に決める（※未決）

### 3.4 継ぎ目の列と倍率の上限

- 継ぎ目の列は出力ラスタの画素の列（JPEG の画素）。ADR-0036 決定1 の 10 の「原寸の列」は、v2 では v2 の出力ラスタの列と読む
- 帯（すべての行で A と B の両方が覆う列）は写像から計算する。v1 の `FixedCompositeOverlapBand` は相似（アフィン）専用なので使えない。v2 は「出力画素→生画素」の写像の対から行ごとに A と B の重なりを求める（4.4 節）
- 初期値は帯の中央（`band-center-provisional`、※仮）。仮の列が帯の中央と一致することは作る時に確かめる。v1 は読むたびに確かめるが、v2 は帯を求めるのに写像の評価が要るので、作る時に寄せる（3.9 節）
- 倍率の上限は v1 と同じく記録の値が正で、方針ファイルとは照合して報告に残すだけ（`ComparePolicyLimit`）

### 3.5 出どころ

- どの校正から作ったかは、profile のファイルの SHA-256 と fingerprint で結ぶ。profile の中に `profileId`、`calibration.provenanceId`、`calibration.tool`、`calibration.inputSha256`（写像を決めた参照の画像の hash）がある。条件にはこれらを写さない（正本を 1 か所にするため）。報告には読んだ profile から取り出して書く
- v1 の `source.reviewReportSha256`・`pairId`・`method` は v2 には無い。v2 の写像は保存済みの review からではなく、校正から作るため

### 3.6 未承認の扱い

v1 と同じ（v1 の設計の 2.2 節）。

- approved を名乗らない。製品の合成（approved だけを受け付ける、ADR-0033 の 4 節、ADR-0034 の不変条件1）に渡さない
- 読む側は既定 OFF の `A0_BUILD_WPD_DUAL_PREVIEW` のビルドで作る WpdDualPreview と StillReview だけ。製品の配布物に入れない
- 記録と画面に「固定の合成条件（未承認・校正の写像）」と出す。報告の品質の三つの false は変えない
- profile は draft のまま。v2 の条件を作っても使っても、profile を書き換えない・承認しない（ADR-0034 の不変条件6）

### 3.7 取り付けの向きと画素の約束

- v2 の写像は、JPEG に保存された順の画素（ADR-0034 の 3、EXIF Orientation は当てない）に対して定義される。#374 の校正もこの順の画素で行う
- 今の開発経路は、`rotated-180` の時に A と B の画素の並びをメモリの中で逆にしてから合成する（`OrientRenderInput`）。v2 では、並びを逆にした画像を受ける時は、写像の側で u = w−1−u′、v = h−1−v′ を合わせて戻す（※案）。並びを逆にするのは画素の入れ替えで、標本化ではないので、resampling は増えない。こうすると経路の作り（向きを当ててから合成へ渡す）を変えずに済む
- 条件の `mountOrientation` は校正した時の向き。今の向き（`wpd-mount-orientation.json`）と違えば、v1 と同じく `orientation-differs` で使わない。向きが変わったなら設置が変わったので、校正からやり直す
- 中心の取り方: v2 の画像の中心は画素の格子の中心 ((w−1)/2, (h−1)/2)。v1 の `FixedScaleCenter` は (w/2, h/2) で、半画素違う。v1 の値は変えない。v2 は ADR-0034 の画素の約束に合わせる（違いは倍率の差 × 半画素で、上限 1% なら 0.01 撮影画素未満）

### 3.8 v1 との並存

| 観点 | 案A: 同じファイル名で、`schema` で分ける（推奨） | 案B: 別のファイル名で両方を置き、v2 を優先する |
|---|---|---|
| 内容 | `wpd-fixed-composite-condition.json` の 1 つだけを読む。`schema` が v1 なら今の関数（#398 の `RenderPairFixedSeam`）、v2 なら文書の写像で描く | v2 のファイルがあれば v2、無ければ v1 |
| 開発速度 | 読む関数が版で振り分けるだけ | 2 つのファイルを探して優先を決める処理が要る |
| 運用コスト | 有効な条件がいつも 1 つで、どちらで描いたかを取り違えない | 「v2 を消したら v1 に戻った」が黙って起きる |
| スケーラビリティ | 版が増えても同じ振り分けで済む | 版ごとにファイル名と優先の規則が増える |
| 学習コスト | 見るファイルが 1 つ | 優先の規則を覚える必要がある |
| 既存スタックとの親和性 | 経路は今のファイル名のまま読む（#400・#401） | 経路に 2 つ目の読み込みを足す |

推奨は案A。案B は、どちらの条件が効いているかを人が追う必要が出るので外した。

- 読む関数は `schema` を見てから、その版の厳密な reader に渡す。v1 の reader（`ParseFixedCompositeCondition`）と v1 の書き出しは変えない
- v1 から v2 へ切り替える時は、人が v1 のファイルを別の名前へ移してから v2 を作る（作る入口は既存のファイルを上書きしない）。どの記録を有効にするかの仕組みが #403 で入ったら、そちらに合わせる
- C と JPEG はどちらの版でも同じ版で描く。セッションの途中で版を切り替えない（C はライブビューを始めるたびに一度読む。#401 と同じ）

### 3.9 読む時に確かめること（※案）

v1 の検証（未知の欄、重複キー、型、`approved` の値の拒否、BOM だけ許す）に加えて:

1. profile のファイルがあり、SHA-256 と fingerprint が一致し、校正済みの draft で、`cameraOrder` が A 左・B 右
2. `outputRaster` が `ValidateOutputRaster`（µm と DPI の切り上げ）と `ValidateCameraProjection`（両カメラ）を通る
3. k = 1 と k = 1 ± 上限/100 で、出力のすべての標本が A か B に覆われる。A の覆う範囲が B より左にある
4. 継ぎ目の列と混ぜ幅の半分が、上の 3 つの k のすべてで、すべての行で A と B の両方に入る
5. `band-center-provisional` の列が帯の中央と一致する
6. 取り付けの向きが今の向きと同じ（経路の側で確かめる）

3〜5 は出力の行ごとに写像を評価するので時間がかかる（出力の行数 × 帯を探す列の数 × 3 通りの k、※推定で 1 秒未満〜数秒）。#400 の JPEG の経路は、撮影のたびに、シャッターの前に、180 秒の期限の中で条件を読む（`SavePairReview`）。そこで検査を分ける（※案）。

- 作る時（8 節）: 1〜5 を全部確かめる
- 読む時（JPEG は撮影ごと、C はライブビューを始めるたび）: 1・2 と、書式の検査だけ。3〜5 は作る時に確かめた写像と同じなので、読む時には繰り返さない
- 合成の中: 継ぎ目の列が重なりに入ること（4.4 節）と、覆えない標本が無いことを、合成の計算そのもので確かめる。外れたら合成しない。profile と条件のバイト列が作った時と同じなら、ここで外れるのは計算の誤りか、壊れた記録だけ

## 4. 合成の関数

### 4.1 写像の形

v2 の合成は、出力画素ごとに各カメラの生画素の位置を 1 本の式で求めて 1 回だけ標本化する（ADR-0034 の 2・4、[rig profile 2.0.0](rig-profile-v2.md) の 7 節）。

```text
X = left + (i + 0.5) * p,  Y = top + (j + 0.5) * p        # 出力画素 → 文書の mm
(X', Y') = (X, Y)                                          # A
(X', Y') = P + ((X, Y) - P) / k                            # B（5 節の倍率。k = 1 なら何もしない）
(u, v)   = TryProjectDocument(カメラ, (X', Y'))            # 文書→画像→歪み→生画素
（C だけ）(u, v) = S(u, v)                                 # 撮影画像の生画素 → ライブビューの画素（6 節）
（向きを当てた画像だけ）(u, v) = (w-1-u, h-1-v)            # 3.7 節
```

この全体を、カメラごとに 1 つの `render::OutputToCamera`（出力の標本の位置 → 生画素の位置）にする。今の `DocumentOutputToCamera` が最初の 2 行と `TryProjectDocument` に当たり、ゲートの `DocumentSeamGeometry` と合成の `RenderDocumentPair` が既に共有している。v2 はこれに B の倍率と、C の `S` と、向きの戻しを足した作り手を 1 か所に置く（`MakeFixedCompositeMaps`、名前は案）。JPEG、C、ゲートはこの作り手が返した同じ関数の対を使う。

### 4.2 案の比較

| 観点 | 案A: #398 の混ぜる部分を写像の対で一般化（推奨） | 案B: `RenderMappedPair` に縦 1 本の継ぎ目と明るさを足す | 案C: B を A の画素（または文書）へ一度写した画像を作り、#398 に渡す |
|---|---|---|---|
| 開発速度 | #398 の帯の標本化・明るさ・合成はそのまま。入口の画素の取り方だけを差し替える | 明るさの比の計算を document_render にもう 1 つ書く | 速い |
| 運用コスト | v1 と v2 で明るさの計算が 1 つ。C と JPEG の見え方がずれる所が増えない | 明るさの計算が 2 つになり、v1 と v2 でずれうる | 中間画像の分だけメモリが増える |
| スケーラビリティ | 将来の写像（承認済み profile の写像、#45）も同じ関数に渡せる | 同左 | 同左 |
| 学習コスト | 「写像の対を受ける」はゲートと同じ形 | 混ぜ方が 2 系統になる | 簡単 |
| 既存スタックとの親和性 | ゲートの `SeamGateGeometry` と同じ `OutputToCamera` の対 | `RenderMappedPair` の feather の試験に影響する | ADR-0034 の不変条件4（resampling 1 回、中間画像を作らない）に反する |

推奨は案A。理由:

1. ADR-0037 の不変条件5（C と JPEG は同じ合成の関数を通る）を、v1 と v2 の間でも守れる。明るさの比、混ぜ幅、飽和の扱いが 1 つの実装になる
2. 合成とゲートが同じ形の写像（`OutputToCamera` の対）を受けるので、「ゲートは書き出す合成と同じ写像で測る」（品質ゲートの 3.2 節）を型の上で揃えられる
3. resampling は 1 回のまま（4.5 節）

案B は明るさの計算が 2 つになるので外した。案C は ADR-0034 の不変条件4 に反するので外した。

### 4.3 推奨の作り（※案、細部は実装の Issue）

- `seam_blend.cpp` の中の `Frame`（A は平行移動、B は逆の射影）を、「出力の (x, y) から A・B の生画素を返す」二つの写像を持つ形に一般化する。v1 用の写像は今の算術を同じ double の計算の順で返すように作り、v1 の出力のバイト列が変わらないことを試験で確かめる（9 節）。v1 の写像は内部では関数オブジェクトを型で持ち、`std::function` の呼び出しの重さを v1 に持ち込まない
- 公開する関数（名前は案）:
  - `RenderMappedFixedSeam(a, b, MappedFixedSeamInput{width, height, camera_a, camera_b}, seam_column, settings)` — v2 の合成。`SeamBlendResult` を返す（明るさの記録の形は #398 と同じ）
  - `CanRenderMappedFixedSeam(...)` — 合成せずに列が入るかを確かめる（#401 の寄せと #403 のドラッグの範囲で使う）
  - `MappedFixedSeamBand(...)` — 行ごとの重なり（帯の中央と #403 のドラッグの範囲に使う）
- `RenderPairFixedSeam`・`CanRenderFixedSeam`・`RenderPairSeamCut` の宣言、振る舞い、試験（`m2_seam_blend_contracts`）は変えない
- 補間は bilinear（`render::SampleBilinear`、被覆は [0, w)）。#398 と同じで、`RenderDocumentPair` の bilinear とも同じ標本点の約束

### 4.4 帯と継ぎ目の確かめ

- v1 の帯は相似の写像の外接の長方形から列の範囲を決め、その中を標本化している。v2 の B の写る範囲は文書の上で曲がった枠になるので、行ごとの重なりは写像を評価して求める
- ゲートの `OverlapBand` が、写像の対から行ごとの重なりを粗い走査と端の詰めで求めている（各行で重なりは 1 続きという前提）。同じ求め方を v2 の帯に使い、求め方を 1 か所にする（`render` の側に置き、ゲートもそれを呼ぶ形が望ましい。ゲートの試験の結果が変わらないことを確かめられる時だけ移す。※案）
- 重なりが 1 続きでない行を見つけたら、合成せずに失敗にする（黙って片方を選ばない）
- 継ぎ目の列が混ぜ幅の半分を含めてどこかの行で重なりから出る時は、v1 と同じく合成しない（`seam-outside-overlap`）

### 4.5 resampling 1 回

- 出力の画素は、生画素から 1 回だけ標本化する。倍率の補正、`S`、向きの戻しは写像の式の中の座標の計算で、画素を作らない
- 倍率の推定（5.3 節）は生画素のタイルの照合で、合成の画素を作らない
- C の画素の位置の表（6.3 節の座標の表）は座標の表で、画像ではない

## 5. 倍率の撮影ごとの補正

### 5.1 掛ける段

| 観点 | 案1: 文書の面で B に掛ける（推奨） | 案2: B の内部パラメータの焦点距離に掛ける | 案3: B の文書→画像の射影に、画像の上の拡大を掛ける |
|---|---|---|---|
| 式 | B の文書座標を P を中心に 1/k 倍してから射影 | fx・fy を k 倍（主点まわり）。射影の行列は K を通して合わせ直す | H_B の前に、歪みのない画像の上の拡大を掛ける |
| 物理の対応 | 高さの違い（文書までの距離の変化）に近い | ピントの合わせ直し（焦点距離の変化）に近い | 両者の間 |
| 中心 P との関係 | 所有者の決定の「出力へ移した点」がそのまま文書の点として使える | 中心は生画素の主点で、出力の点ではない | 中心は歪みのない画像の点 |
| 開発速度 | 写像の作り手に座標の計算を 1 段足すだけ | K と H を撮影ごとに作り直す計算が要る | H に行列を掛けて正規化し直す計算が要る |
| 運用コスト | profile の値を変えないので、報告は k と P だけを持てばよい | 撮影ごとに K が変わり、報告に「当てた K」を別に残す必要がある | 撮影ごとに H が変わり、同左 |
| スケーラビリティ | 文書座標の相似を先に掛ける段なので、将来ほかの補正を足す時も同じ段に入る（今の決定では倍率だけ） | 倍率のほかは表せない | 画像の上の相似までは表せる |
| 学習コスト | rig profile 2.0.0 の 7 節と同じ説明で済む | レンズの模型の説明が要る | 2 つの間の説明が要る |
| 既存スタックとの親和性 | [rig profile 2.0.0](rig-profile-v2.md) の 7 節が、撮影ごとの補正をこの段に置くと定めている | 7 節と違う段になる。#374 の K は公称値で「K と係数は組で使う」（[平置きの推定](../M2_PLANAR_CALIBRATION.md) の 7 節）ので、K を動かすと組が崩れる | 7 節と違う段 |
| 推定との一致 | 推定も文書の mm で行うので、推定と当てる段が同じ | 推定を生画素で行う必要がある | 推定を歪みのない画像で行う必要がある |

推奨は案1。理由:

1. ADR-0034 が参照する設計（7 節）の段そのままで、ADR の改定が要らない。案2・案3 は 7 節と食い違うので、採るなら設計と ADR-0034 の改定が要る
2. 所有者の決定の中心「B の画像の中心を固定の写像で出力へ移した点」が文書（出力）の点なので、式に直接入る
3. profile の値を変えないので、fingerprint が撮影ごとに変わらない。C、JPEG、ゲートに同じ写像を渡せる

ただし、どの案が実機の倍率の変化に合うかは、変化の原因（ピントか高さか）で変わる。案1 と案2 の差は、倍率の差を δ、放射の係数の寄与を k1·r² として、生画素でおおよそ 2·δ·k1·r²×（主点からの距離）になる（※推定、一次の近似）。継ぎ目はレンズの縁を通るので r が大きく、係数によっては継ぎ目の上下の端で出力の 1 px に届きうる（※推定）。この差は残差としてゲートに出る。実機で倍率の変化とゲートのずれを測った後に、案2 へ切り替えるかを決める（10 節）。切り替えが要る時に直す所が 1 か所で済むよう、B の写像に倍率を入れる所は 4.1 節の作り手だけにする（インターフェースは足さない）。

### 5.2 中心 P の v2 での定義

- 所有者の決定: 補正の中心は「B の画像の中心を固定の写像で出力へ移した点」
- v2 の読み方（※案）: B の画素の格子の中心 c = ((w−1)/2, (h−1)/2) を、B の固定の写像の逆で文書へ移した点 P_doc。つまり、B の固定の写像で c に写る文書の点。出力の画素では P_out = (P_doc − (left, top)) / p − 0.5
- #374 の profile では主点が c にあり、c では歪みが 0（正規化座標が 0 なので歪んだ位置も 0）なので、P_doc = H_B⁻¹(c) の閉じた式で求まる。歪みの逆（反復）は要らない
- 主点が c に無い profile（内部パラメータを推定する #277 の校正など）では、P_doc を求めるのに歪みの逆が要る。その時に「画像の中心」と「主点（光学の中心）」のどちらを使うかは所有者に確認する（15 節の 2）。所有者の決定の理由（倍率は B のレンズの中心のまわりにかかる）からは主点が近いが、決定の言葉は画像の中心なので、この文書では決めない
- 報告には P_doc（mm）と P_out（出力の画素）の両方を書く

### 5.3 推定

| 観点 | 案E1: #400 のタイルを文書の mm へ移して当てはめる（推奨） | 案E2: v2 の写像で A・B を出力の格子に置いて照合する（ゲートの測り方） |
|---|---|---|
| 開発速度 | 推定器（`EstimateOverlapSimilarity`）と判定の形（`DecideFixedScale`）を流用できる | ゲートの測定器を流用できるが、倍率のための当てはめと周期の取り違えの扱いを足す |
| 運用コスト（時間） | 合意したタイルの数だけ歪みの逆を解く。数十点で、合成に比べて小さい（※推定） | 帯の全体を測ると、ゲートと同じ程度の時間（校正済みで約 40 秒、品質ゲートの 16.9 節）がもう 1 回かかる |
| スケーラビリティ | タイルの数は推定器の格子で決まり、出力の大きさによらない | 測る範囲の広さに比例する（#404 の後は継ぎ目の周りだけ） |
| 学習コスト | #400 の説明に「文書の mm へ移す」1 段を足すだけ | ゲートの測り方を倍率の推定にも使う理由の説明が要る |
| 既存スタックとの親和性 | #400 の報告の形（使ったタイルの数、残差、説明できなかったずれ）をそのまま使える | ゲートの報告と測定点を共有できる |
| 正しさ | 推定器の合意（LMedS）は生画素の上の相似で選ぶ。歪みがあると帯の上下の端のタイルが合意から外れうる（※推定） | 写像で歪みを除いた上で照合するので、純粋な拡大のモデルが合う |

推奨は案E1 で始める。理由: 推定と判定の作りを #400 から変えずに済み、時間も小さい。ただし、合意から端のタイルが外れると、k を決める縦の広がり（帯の上下の距離）が短くなる。9 節の人工の歪みの試験で、端のタイルが使われていること（使ったタイルの行の範囲を報告に出す）と、入れた倍率が戻ることを確かめ、戻らなければ案E2 へ切り替える（※案。切り替えの条件は試験の許容で、光学の閾値ではない）。

案E1 の手順（※案）:

1. 推定器の初期位置（平行移動）は、v2 の写像で B の中心 c を文書へ移し、それを A の生画素へ写した位置から作る
2. 推定器は今と同じく、向きを当てた（A 左・B 右に並べた）画像で走らせる。返ったタイルの座標は推定器の約束（画素の角が原点）なので、v2 の約束（画素の中心が整数）へ半画素直し、向きを当てていれば 3.7 節のとおり保存した順の画素へ戻す
3. 合意したタイルの A の点 a と B の点 b を、それぞれの固定の写像の逆（歪みの逆と文書→画像の逆）で文書の mm へ移す（X_a、X_b）。歪みの逆は校正の内部にある `UndistortPixel`（`src/m2/calibration_lens_model.hpp`）を共有できる形に出して使う。収まらない点は使わない
4. 使うタイルの条件は #400 と同じ考え方: 合意に入っていて、X_a と X_b の差が推定器の探索半径を文書の mm に直した値より小さいもの。1 周期ずれた一致はここで落ちる
5. q = X_b − P_doc、t = X_a − P_doc として t = k·q + d を最小二乗で解く（#400 と同じ式）。回転は固定の写像の値に縛る。v2 では A と B が同じ文書座標に置かれているので、縛る回転は 0
6. 判定は #400 と同じ: |100k − 100| が上限以下なら当てる、超えたら当てずにゲートで不合格・案内、推定できなければ当てない。当てた後に 3.9 節の 4（継ぎ目が重なりに入る）を確かめる。3.3 節のとおり、上限の範囲の k では出力の覆いと継ぎ目は作る時に確かめてあるので、ここで外れるのは条件が壊れている時だけ
7. 当てるのは k だけ。d は「倍率で説明できなかったずれ」（mm と出力の画素）として報告に残す

v1 との違い: v1 は A の生画素の上で当てはめるが、v2 は文書の mm の上で当てはめる。歪みを除いた座標で当てはめるので、端のタイルの歪みが k に混ざらない。

## 6. C（#401）

### 6.1 写像の順

- `S` はライブビューの画素と撮影画像の画素の対応（拡縮と平行移動）で、今の仮定は #401 と同じ（ライブビューの frame が撮影画像の全体を縦横それぞれの比で縮めて写す。※未検証、#309）
- 歪みの係数は正規化座標の上で定義されていて、その正規化は撮影画像の画素の K で行う。そこで C の写像は「出力 → 文書 → 撮影画像の生画素（K と係数）→ `S` → ライブビューの画素」の順にする（4.1 節の式）。`S` を K の後ろに掛けるのは、ADR-0036 決定1 の 2 の K_lv = S·K、H_lv = S·H（係数はそのまま）と同じ写像になる（S が拡縮と平行移動だけで、K に傾きの項が無いため）。式を 1 本にして、撮影画像の画素の K で計算した値に S を掛ける形にすると、JPEG と同じ射影の関数を使える
- `S` の形は #353 の `StillToLiveMapping`（保存した順の画素の番号で live = scale × still + offset、半画素の offset を自動で足さない）に合わせる。値は #401 の仮定（scale は大きさの比、offset は 0）を入れ、出どころを「未検証の仮定」と記録する。#353 の `RenderPreviewForEvaluation` は人工の対応しか受け付けないので、C はそれを使わず、4 節の合成関数に `S` を含めた写像を渡す（評価用の入口の検査は緩めない）
- 倍率は補正しない（撮影の前に倍率を知らない、ADR-0037 の決定6）

### 6.2 C の出力格子と継ぎ目の列

- C の出力は、JPEG と同じ文書の領域を、間隔 p_C = p / s で区切った格子にする。s は JPEG の出力に対する縮尺（v1 の C と同じく、撮影画像に対するライブビューの縮尺 sx を使う。※案）。DPI は整数でなくなるので `OutputRaster` は使わず、写像の関数の中で X = left + (i+0.5)·p_C とする
- C の列数は、領域の中に収まる数（切り捨て）にする。JPEG で覆えることを確かめた領域の中の点だけを標本にするため。それでも被覆が足りない標本があれば C を描かず理由を出す（ADR-0036 決定1 の 8 の考え方、#401 と同じ）
- 継ぎ目の列: JPEG の列 c の中心と同じ文書の X を通る C の列は (c + 0.5)·s − 0.5。これを丸め、#401 と同じく左右 2 画素まで近い順に `CanRenderMappedFixedSeam` で確かめて寄せる。寄せた量は画面に出す
- 混ぜ幅と明るさの窓の縮め方は #401 の `ScaleSeamBlendSettings` をそのまま使い、縦横とも s を渡す（C の格子は文書の上で縦横同じ間隔なので）。C 用の別の定数を持たない
- ライブビューの縦横の比が撮影画像と違っても、`S` の縦横の倍率の違いは写像の中で扱われ、C の格子は文書の上で正方のまま
- #403 のドラッグ: C の列 i から JPEG の列へは (i + 0.5)/s − 0.5 を丸める。保存するのは JPEG の列（v2 の出力ラスタの列）

### 6.3 計算量（※推定）

- C の出力は、JPEG の出力の縦横を s 倍した大きさ（v1 の C と同じ程度。数十万画素）。v2 で増えるのは標本ごとの射影（3×3 の射影、正規化、5 係数の多項式、`S`）で、1 標本あたり数十回の乗算
- 写像はセッションの間変わらない（ライブビューを始める時に条件を読み、そのセッションでは変えない、#401）。そこで、出力画素ごとの A・B の生画素の位置を、セッションの初めに一度だけ座標の表にしておき、frame ごとには表を引いて標本化するだけにできる（数十万画素 × 2 カメラ × 2 座標で数 MB）。表は座標で画像ではないので、resampling は 1 回のまま（4.5 節）
- 表を作るかどうかは、開発用の PC で frame ごとの時間を測ってから決める。表を作らずに ADR-0036 決定1 の 9 の見込みに収まるなら作らない（作りを増やさない）
- JPEG の出力は数千万画素の規模（※推定）。継ぎ目の左は A だけ、右は B だけを射影し、帯の中だけ両方を射影する（#398 の合成の作りと同じ）。行ごとに独立に計算できるので、行で分けて並列にしても結果は同じにできる。180 秒の期限の中でゲートと合わせて収まるかを測る（14 節のリスク）

### 6.4 表示専用の制約

- C の画素は保存しない。撮影、保存の合成、補正の推定、条件・profile の入力にしない（ADR-0036 決定1 の 5）
- 座標の表は条件と profile だけから作り、ライブビューの画素から推定しない
- frame ごとに求める明るさの比は表示にだけ使う（決定1 の 3）
- C の画面で人が動かした列を条件に保存するのは、決定1 の 5 に当たらない（#396 の C1）。v2 でも同じ
- 画面の注記: 「ライブビューと撮影画像の対応は ※未検証（#309）」「倍率は補正しません」「保存しません」に加えて、「校正の写像（draft、未承認）」と profile の識別子を出す

## 7. ゲート（#385・#404）との関係

- ゲートは `SeamGateGeometry`（出力の大きさ、A・B の `OutputToCamera`、測る帯、遷移帯）を受けて、A と B を別々に置いて測る。v2 の合成が使う写像の対（倍率 k を入れた後の B を含む）を、そのまま `camera_a`・`camera_b` に渡せる。`DocumentSeamGeometry` は倍率を入れられないので、4.1 節の作り手からゲートの形を作る関数を足す（※案）
- 遷移帯は、すべての行で同じ列の道筋を `SeamCutTransitionBand` に渡して作る（v1 の設計の 9 節と同じ）
- 測る帯: #404 の前は今の `OverlapBand`（校正済みの内側への幅）。#404 の後は「継ぎ目の列 ± 混ぜ幅 ＋ 余裕」。どちらでも写像は同じものを渡す
- 設計定数: v2 は校正済みの写像なので、ゲートの校正済みの定数（最初の探索半径など）を使うのが筋（※案）。ただし今の draft では両端のずれが大きく、探索の端に当たって広げる測り直しが増え、時間が延びうる。WP-04 で決める
- 1 px は書き出す画像の画素（#385 Q2）なので、v2 では出力ラスタの DPI の画素で数える（3.3 節）
- 順番: v2 と #404 の間に依存は無い。WP-04（ゲートを開発経路へつなぐ）には両方が要る。#404 は #394 の再開と一緒に進める予定のままでよい

## 8. 作り方の入口

- StillReview の開発用 CLI に、v1 の `--make-fixed-composite-condition` と並べて v2 の作り方を足す（※案）:

```text
StillReview --make-fixed-composite-condition-v2 --profile <draft profile> --settings-folder <フォルダ>
            --region-um <left,top,right,bottom> --dpi <整数>
```

- 人が設置の時に明示して一度だけ作る。撮影の結果から自動で作らない（ADR-0037 の決定5）
- 手順:
  1. 方針ファイル（`wpd-merge-policy.json`）から倍率の上限を写す。無い・欄が無い時は作らない（v1 と同じ）
  2. 今の取り付けの向き（`wpd-mount-orientation.json`）を記録する
  3. profile を読み、3.9 節の 1〜5 を確かめる。帯の中央を仮の列にする
  4. profile を設定のフォルダへ写す（3.2 節。上書きしない）。条件を新しいファイルとして書く（v1 の `WriteFixedCompositeCondition` と同じ手順。既にあれば作らない）
- 領域と DPI に既定値は持たない。人が渡さなければ作らない。代わりに、渡された profile から次を表示する（作る前の確認用。値は記録しない）: 両カメラの覆う範囲の外接と、すべての行で覆える長方形の候補（文書の mm）、帯の列の範囲、継ぎ目のあたりで 1 撮影画素に当たる DPI
- 入力は #374 の `RunPlanarCalibrationJob` が書く draft profile。校正の報告（継ぎ目の食い違い、覆う範囲）は入口では読まない（profile の `calibration.provenanceId` で結ばれている）。画面と報告に profile の識別子を出す
- C の画面から作り直す入口（列の改訂）は #403 の範囲

## 9. 試験の方針

カメラを使わない。人工の画像と人工の写像だけで確かめる。許容は試験の固定の値で、光学の受入の閾値ではない。

**v2 の記録（W1）**
- 書式の全文と往復
- 読む時の拒否（3.9 節の 1・2 と書式）: 未知の欄、`approved`、profile が無い・hash が違う・fingerprint が違う・校正の値が無い draft・approved の profile・上下の配置、画素数の不一致
- 作る時の拒否（3.9 節の 3〜5）: k の上限の端で覆えない領域、帯の外の列、仮の列が中央でない、既にあるファイルへの書き込み
- profile の参照: 区切りや親のフォルダを含む名前を拒否する

**合成の関数（W2）**
- v1 が変わらないこと: 一般化の前後で、既存の試験（`m2_seam_blend_contracts`、`m2_fixed_composite_condition_contracts`、`preview_fixed_composite_contracts`、`still_review_contracts`）がそのまま通る。加えて、一般化の前に `RenderPairFixedSeam` の出力と記録の SHA-256 を人工の入力（回転と倍率つきを含む）で固定しておき、後で同じになることを確かめる
- 歪み 0 の v2 の写像で、A・B の配置が v1 の相似と同じになる人工の組では、継ぎ目と明るさの記録が一致する（画素は補間の座標の丸めの範囲で一致）
- 同じ入力で 2 回、スレッド数を変えて同じバイト列

**歪みの効果（W2・W4）**
- #374 の試験の `--write-fixture` が書く真の profile と人工のペア（`SyntheticPairGenerator`、放射の歪みあり）を使う
- v2: 真の profile と、#374 の推定で作った draft の 2 通りで条件を作って合成する
- v1: 同じペアに #365 の推定から作った相似で v1 の条件を作って合成する
- ゲートの測定器（`MeasureSeam`）を、合成と同じ写像の対と遷移帯で走らせ、行を上の端・中ほど・下の端に分けて最大のずれを比べる。v2 の両端の最大が v1 の両端の最大より小さいこと、真の profile の v2 では両端も中ほども試験の許容の内にあることを確かめる

**倍率（W3）**
- 真の写像の B に P_doc を中心とした既知の倍率（上限の内と外）を入れた人工の組で、推定した k が許容の内で戻り、上限の内なら当て、外なら当てないこと
- 端のタイルが使われていること（使ったタイルの行の範囲）
- 繰り返し模様だけの帯で「推定できない」になり、補正しないこと
- 中心 P が、真の写像で B の画像の中心に写る文書の点と一致すること

**C と JPEG の幾何の一致（W5）**
- 同じ v2 の条件から作った C の写像と JPEG の写像で、C の画素 i の中心と同じ文書の点を JPEG の写像に入れて `S` を掛けた位置が、C の写像の値と一致すること（画素ではなく写像の値で比べる）
- 継ぎ目の列の対応が丸めと寄せ（2 画素）の範囲にあること。#401 の試験と同じく、帯の両端の近くの列と中央の列で確かめる

**時間（測るだけ）**
- 撮影画像の大きさの人工の組で、JPEG の合成、倍率の推定、条件の読み込み（3.9 節）の時間と、C の 1 frame の時間（座標の表の有無）を測って記録する。合否は付けない

## 10. 実機の作業と、それまでにできること

実機の作業（※この Issue では行わない。実施の前に対象・回数・手順の承認が要る）:

- 配置が決まった後の校正のやり直し（H1）。画面の角と、継ぎ目の上下の端まで点が写るように、平置きのチャートを置いて撮る（[校正の撮影の手順](../CALIBRATION_CAPTURE_PROCEDURE.md) の平置きの手順）。#374 の限界（範囲の縁と隅に点が無いと外挿になる、継ぎ目の上下の端の食い違いは測れていない）を埋めるため

- `S` の実測（#309）。C の列と JPEG の列の対応はそれまで ※未検証

- W1〜W6 の実装と 9 節の試験

- 吊り下げの配置は外してあり、戻すかは決まっていない。val02 の条件を今の機材の C に使うと、写像が合わない絵になる。実機の C で v2 を見るのは、配置を決めて校正し直した後にする

## 13. 守るべき不変条件

1. 合成の写像（倍率以外）と継ぎ目の列は、撮影や frame の内容で変えない（ADR-0037 の不変条件1）。v2 では profile と条件の出力ラスタが変わらない限り、同じ写像を使う
2. JPEG、C、ゲートは、4.1 節の作り手が返した同じ写像の対を使う。B に倍率や `S` を入れる所は作り手の 1 か所だけ
3. v1 の reader、writer、合成の出力のバイト列、報告の版は変えない
4. 有効な固定の合成条件は 1 つで、版は `schema` で決まる。v1 と v2 を混ぜて描かない
5. profile は校正済みの draft、ファイルの SHA-256 と fingerprint が条件と一致するものだけを使う。approved の profile を開発経路の条件に入れない。条件も profile も承認しない
6. 出力のすべての標本は、上限の範囲のどの k でも A か B に覆われる。覆えない領域の条件は作らない・使わない
7. resampling は 1 回。中間の画像を作らない
8. 領域、DPI、倍率の上限、レンズ係数にコードの既定値を置かない。欄が無ければ失敗にする
9. C の画素は保存せず、推定と条件の入力にしない。座標の表は条件と profile だけから作る
10. 合成できない時（条件が無い・壊れている・profile が無い・hash が違う・向きが違う・列が重なりの外）は合成せず、原画像は残す（v1 と同じ）

## 14. リスク

- **校正の端の誤差**: v2 は相似で表せない歪みを直すが、校正が外挿している所（帯の上下の端）の誤差は残る。今の draft のままでは、両端のずれが合格線を超えたままになる見込み（※推定）。10 節の校正のやり直しが要る
- **倍率のモデル**: 5.1 節のとおり、ピントの変化と高さの変化で正しい段が違う。違いは帯の上下の端に出る
- **推定器の合意**: 案E1 では、歪みのために端のタイルが合意から外れ、k が中ほどのタイルだけで決まりうる（9 節で確かめ、だめなら案E2）
- **時間**: JPEG は帯の外も含めて全画素で射影を計算する。ゲートと合わせて 180 秒の期限に収まるかは測るまで分からない（※未計測）。収まらない時は、行で分けた並列化と、ゲートの範囲の縮小（#404）で詰める。射影を近似（粗い格子の補間など）に替えると C と JPEG の写像が変わるので、替えるなら両方を同時に替え、試験の期待値も替える
- **期限の中の読み込み**: JPEG の経路は条件をシャッターの前に期限の中で読む。v2 では profile の読み込みと fingerprint の計算が加わる。重い検査を作る時に寄せた（3.9 節）のはこのため
- **ファイルが 2 つ**: 条件と profile の片方だけを移す・消すと使えなくなる。合成しない側に倒し、理由を出す
- **出力の向き**: #374 の文書座標はチャートの座標なので、チャートを斜めに置いて校正すると出力も斜めになり、縦一直線の継ぎ目が取れる列の範囲が狭くなる。作る前の表示（8 節）で帯の範囲を確かめる
- **DPI とゲートの意味**: DPI を下げると、ゲートの 1 px が文書の上で長くなり、合格しやすくなる。DPI を決めずに比べると、v1 と v2 の比較を誤る
- **`S` の半画素**: `S` の offset を 0 とする仮定は、画素の中心と角のどちらで縮めたかで半ライブ画素ずれうる。#401 と同じ仮定に乗っており、#309 で測るまで C の列の位置は ※未検証

## 15. 所有者に確認が要る点

1. **写像の持ち方**: v2 の条件は draft profile を SHA-256 と fingerprint で参照し、値は持たない（3.2 節の案A）。これでよいか
2. **中心 P**: v2 では、B の画素の格子の中心を B の固定の写像の逆で文書へ移した点とする（#374 の profile では主点と同じ点）。将来、主点が画像の中心に無い校正（#277 など）を使う時は、画像の中心と主点のどちらを中心にするか
3. **倍率を掛ける段**: 文書の面で B に掛ける（5.1 節の案1、rig profile 2.0.0 の設計 7 節どおり）。実機でピントと高さの変化を測った後に見直す前提でよいか
4. **開発用の出力ラスタ**: 領域と DPI は人が作る時に渡す未承認の値とする。DPI は v1 と比べるために撮影画像と同じ程度の細かさにするか、#42 の候補（A0 横 180 DPI）にするか。ゲートの 1 px の意味が DPI で変わる
5. **出力の大きさを撮影ごとに変えない**: v2 は倍率の上限の範囲のどの k でも覆える領域を作る時に確かめ、出力の大きさを固定する（v1 は k で出力の窓が少し変わる）。これでよいか
6. **ADR-0036 決定1 の 7 の読み方**: draft profile から作った v2 の条件で、開発用のビルドの C を描くことは、決定1 の 2 の副項（固定の合成条件で描く開発経路）に当たり、決定1 の 7（draft の profile で C を描かない）に反しない、と読んでよいか
7. **v1 から v2 への切り替え**: 同じファイル名の 1 つだけを有効にし、切り替えは人が v1 のファイルを移してから v2 を作る（#403 の有効な記録の選び方が入るまで）。これでよいか
8. **保存済みの組と val02 での確認**: カメラを使わずに、保存済みの非公開の組と val02 で v2 の経路を通す確認をしてよいか（結果の値は公開しない。品質の判定にしない）
9. **子 Issue の分け方と順番**: 11 節の W1〜W6 と、#403・#402・#394 との順番
