# 撮影の 1 組から校正を取り直す（#434）

カメラの間隔を変えた時に、レンズの校正を最初からやり直さず、1 組の撮影だけで CAM-B の写像を取り直して新しい条件の改訂を足す。この文書は計算の部分（`src/m2/fixed_composite_recalibration.*`）の設計と決まりを書く。画面と確定の書き込みは別の層の仕事で、ここでは扱わない。書式は `fixed-composite-registration-formats.md`、profile の欄は `rig-profile-v2.md` の `/calibration` の注、改訂の種類は `fixed-composite-registration.md` の 11.19.3。

## 1. 何を変え、何を変えないか

- 変えない: レンズ（K と 5 係数）、CAM-A の写像、撮影の経路、方針ファイルの値、`seam_gate.*`、前の改訂と前の profile（消さない・上書きしない）
- 変える: CAM-B の「文書 → 画像」の写像だけ。両台で撮った 1 組から B の姿勢 p-hat（6 自由度）を求め、`PoseModel(B).CameraHomography(p-hat)` を B の `documentToImage` にした新しい draft profile を作る。A のブロックは親のまま。新しい profile では p_b = 0
- 新しい条件は改訂として 1 つ足す（種類 `recalibrated`）。profile・出力ラスタ・継ぎ目の列を親と変えてよい唯一の種類

p_b に大きな値を入れずに profile を作り直す理由: p_b は「校正から範囲の内」が撮影とライブの読み手の決まりで、範囲を超える移動を p_b に入れるとこの決まりを崩す。profile に焼き込めば決まりはそのままで、範囲も新しい位置が中心になる。写像としては同じ（H0 · G(p-hat) = H(p-hat)）。

前提: 間隔を変える時、レンズ（焦点距離・ピント）と A の向きは変えない。広げるのは B を基線の向きへ動かすこと。これが崩れた時（B が振れた、高さやズームを変えた）は 5 節の線で確定させない。

## 2. 流れ

| 段 | 関数 | 中身 |
|---|---|---|
| R1 広く探す | `EstimateWideStart` | 原画像 2 枚で重なりを広く探す（`EstimateOverlapSimilarity`。重なりが幅の 10〜90 %）。合意したタイルの点を A・B それぞれの校正の写像の逆で文書の mm へ移し、文書面の剛体のずれ（tx, ty, rz）を最小二乗で求めて初期の姿勢 p0 とする。半回転の取付は画像を回してから探し、点を保存順へ戻す。重なりが決まらない時だけ `no-overlap`（理由は R1 の理由）。R1 が決めた p0 の動き（左右・上下・回り）は、R2 の姿勢が無い断りでも「目安」として画面と報告に出す |
| R2 細かい合わせ | `ProposeRecalibration` の内 | `EstimateRegistration` を 6 自由度（紙面なし）で、base_pose = p0、条件の範囲・閾値・幾何で回す。`verified` が要る。出力ラスタは p0 で 3 節の決め方で決め、継ぎ目の列はその p0 での重なりの帯の中央（`keep_previous` なら親の列）。ラスタか帯が取れなければ R2 は回らない（`band-uncovered`・`range-collapsed`） |
| R3 焼き込み | `ReanchoredProfileText` | 新しい draft profile の文字列。`RigProfileV2::Parse` を通す |
| R4 作る時の検査 | `ProposeFromPose` | 出力ラスタ（`ProposeRaster`。右端は B の動きに合わせ、上下は B が写る行まで縮める。3 節）と継ぎ目を決め、親の値を詰めた要求で `MakeFixedCompositeConditionV3`（ファイルを読まない純粋な関数）を呼び、`MakeFixedCompositeCreationCheckV3` を通す。検査の判定と文は変えない |
| 確かめ | `VerifyCandidate` | 新しい profile で製品と同じ設定の推定をもう一度回し、継ぎ目の列の上のずれを測る（5 節の 3） |
| R5 見本 | `SelectionOfCandidate` | 候補をメモリの中の selection にする。合成は既存の関数（撮影の経路が使う `ComposePairWithSelection`）に渡す |

`ProposeRecalibration` は R1 から確かめまでをつなぐ。ファイルを読まず、書かない。時刻、SHA-256 の提供、推定器の設計定数、停止の合図は呼び手が渡す。

## 3. 継ぎ目の列と出力の範囲

どちらも切り替えられる作りで、既定は所有者が選んだ側（継ぎ目は重なりの真ん中、範囲は B に合わせる）。A と B を同時に動かして間隔を広げる使い方もあるので、画面と案内の文は「B を動かした時」と決め打ちせず、「カメラの間隔を変えた時」「A に対する B の位置」と書く。

| 選ぶ物 | 既定 | もう一方 |
|---|---|---|
| 継ぎ目（`SeamPlacement`） | `band_center`: 新しい profile での重なりの帯の中央。origin は `band-center-provisional`。撮るたびの合わせ込みが一番効く | `keep_previous`: 親の列（図面の上で同じ位置）。origin は `operator`。重なりの端に近くなると検査 (a) で落ちて確定させない |
| 出力の範囲（`RasterPlacement`） | `follow_camera_b`: 左端と DPI は親のまま。右端は B の覆いの右端が動いた量だけ動かし（広げた分だけ広げる）、上端と下端は B が写る行まで縮める（広げない）。決め方は 3.2 | `keep`: 親のまま（広げた分は合成に入らない）。上下にずれて B が写っていない行が出る時は `band-uncovered` で断る |

### 3.1 所有者の決定（#439）

次の 4 つは所有者が決めた。変えるには所有者の決定が要る。

1. 校正を取り直した時、カメラが上下にずれていた分までは、合成の範囲の高さが縮んでよい。縮んだ量は mm で必ず画面と報告に出す。確定のボタンは今のまま（高さが縮む時も、確認の段は増やさない）
2. 見せ方は、画面の「合成の画像の大きさ」の行に、高さの前と後と、「図面の下（または上）の約 N mm は合成に入りません」を足す。判定の行（1 行目）には添えない
3. `follow_camera_b`（範囲は B に合わせる）に上下の追従も含める。別の設定は足さない。`keep` は今のまま
4. #439 は、手元の main を公開する前に入れる。校正の報告の書式は v1 のままにする（6 節）

### 3.2 範囲の決め方（設計が決めた細部）

3.1 の決定を実現するために設計が決めた。所有者の決定そのものではなく、実装と試験で守る。

- **縮めるだけで、広げない**: 上端と下端は親の外へ広げない。A の覆いは動かないので、親の上下の外は A が写る保証が無い。縮む量の下限は置かない（線を置く時は所有者の決定が要る）。左端と DPI は親のまま
- **今の流れが通る組は今のまま（門 1）**: 親の全行で帯が取れ、その中央の列で、作る時の検査が名指しで断る条件（全行・基準の姿勢と範囲の軸の両端で、継ぎ目の列が A と B の両方に写り、A が継ぎ目から混ぜ幅の半分先の列まで写る）が成り立つ組は、上下を動かさず、右端だけを下の「右端」の決め方で動かす。どの行も B の覆いが B の右の辺で終わる組（左右だけ動かした組の多く）では、結果（範囲・継ぎ目・B の写像・候補の文字列とハッシュ）がビットで今と同じになる。門 1 は検査の必要条件で、十分条件ではない。門 1 を通って削らない組を、検査が範囲の頂点を数えて断る事がある（9 節）
- **門 1 の継ぎ目の列**: 候補と作る時の検査が使う関数（`FixedCompositeProvisionalSeamColumn`。右端だけを動かした範囲と B の新しい写像）で出す。全行の帯が取れずにこの関数が投げる時は門 1 を飛ばす（その範囲は作る時の検査が断る）。継ぎ目を親の列に置く時は親の列
- **削る量は、B がずれた分まで**: 削ってよい量は、継ぎ目の列の上で B が写る上の端と下の端が、親から新しい位置へ動いた分。親は親の姿勢と親の継ぎ目の列、新しい位置は新しい姿勢と、新しい継ぎ目が来うる一番左の列（継ぎ目を親の列に置く時は親の列）で、どちらも範囲の頂点を足さない名目の姿勢で求める。端は真ん中の行から外へ探し、範囲の外は 1 範囲の高さまで探す（削る量は範囲の高さを超えないので、それより先は答えを変えない。合格の線ではない）。行数は切り捨て。B が回って継ぎ目のあたりで写る端が動いた分も、上下のずれと同じに数える。左右だけ動かした組は、検査が通るなら門 1 で削らない。門 1 を通らない組でも、削ってよい量は継ぎ目の列で B の端が動いた分だけなので、左右に広げすぎた分を高さで払わない（今と同じ `creation-check-failed` で断る）。B が左右にも上下にも動いた組では、継ぎ目の列と B の中心の距離が変わって検査の届きが親と違い、ずれた分だけ削っても検査が断る事がある。その時も、ずれた分を超えて削らない。新しい継ぎ目の列は親の位置で写るかを見ないので、B が左へ動いた組（重なりが広がる）も止めない
- **残す行**: 継ぎ目が来うる列の左右（混ぜ幅の半分と浮きの上限を足した幅）の上で、作る時の検査と同じ範囲の頂点の全部で B が写る行の共通部分（真ん中の行を含む 1 続きの区間）。共通部分が空なら削らず、後の段（帯の検査か作る時の検査）が断る。作る時の検査のもう 1 つの条件（範囲の最後の列が A か B に写る。紙面の範囲は含まない）も同じ形で見る: 見る列は新しい範囲の最後の列（残す行で右端を決めた幅の最後の列）で、A がその列を残す行の全部で写さない時は、範囲の頂点（紙面なし）の全部で B がその列を写す行に絞る。この絞り込みは 1 回だけで、それでも条件が成り立たない範囲は作る時の検査が断る。範囲の右端が B の右の辺に近く、真ん中の行でもどれかの頂点で B がその列を写さない時は、この条件では行を選べないので絞らない（作る時の検査が決める）。頂点は検査が強制する範囲（円盤）に外接するうえ、検査は線形の予測が外れた所でしか頂点を数えないので、頂点で選んだ行は検査が要る行より少なくなりうる。最後に、削る量が上の「B がずれた分」を超える側を、その分まで外へ戻す（上の端の行は残す行の上端と上で削ってよい行数の小さい方、下の端の行は残す行の下端と「全行の最後の行 − 下で削ってよい行数」の大きい方）。全行に戻った時は削らず、右端だけを動かした範囲を返す。最後は作る時の検査が全行・全範囲で見て決める。範囲の頂点の一覧と、軸の両端の点（検査が継ぎ目の列を写さない行を名指しで断る点）は、`fixed_composite_creation_v3` から公開して使い、定義は 1 か所に置く。継ぎ目が来うる列の幅は、重なりのある行の帯から決める（左端は全行の最小、右端は残す行の最大。継ぎ目を前の列に置く時はその列）。行は、右端だけを動かした範囲ではなく、今の改訂の範囲の上で選ぶ（右端を全行で決めた範囲は、回りがあると極端に狭くなりうるため）。門 1 だけが、右端だけを動かした範囲を見る。A の縁で欠ける行は削る理由にしない（作る時の検査を通った親では、A は全行を写す）
- **上下の端の丸め**: μm の整数で、どちらも内側へ丸める。画素数は `ValidateOutputRaster` の式
- **右端**: 親の位置と新しい位置を、残した同じ行（削らない時は全行）で比べて決める。各行の右端は B のセンサーの横の端（保存した画素の x が 0 以上・センサーの幅未満。y は見ない）だけで求めるので、回りで斜めになった B の上下の辺が行を横切る所では決まらない。回りでは、残した行の端で B の右の辺が引っ込んだ分だけ幅が狭まる（B が実際に写さなくなった分。量は画面と報告に出る）。この取付の 2 つ（通常・半回転）では、センサーの横が図面の横になる。これを親の姿勢の真ん中の行で確かめ（覆い全部の右端と横の端だけの右端が一致する事）、一致しない時は今の式（覆い全部の右端の、全行の最小）で右端だけを動かし、削らない。どの行も B の右の辺で終わる組（左右だけ動かした組）では、二つの式は同じ数になる。4 台の 2×2 で縦向きの取付が出たら見直す。範囲の右下の角を B が写すかは、上の最後の列の条件と作る時の検査が見る。幅が 1 画素未満になる時は `range-collapsed`、描画の限界を超える時は `raster-too-large`
- **継ぎ目の列**: 既定（帯の中央）は新しい範囲の帯の中央。上下を削ると帯の左端が下がり、列が今より左へ寄る事がある。`keep_previous` は親の列
- **新しい閾値は作らない**: 使う数は条件の範囲、混ぜ幅の設計定数、浮きの上限だけ（どれも作る時の検査が使う物）
- **ライブと JPEG**: どちらも同じ条件のファイルを読む。範囲の変化は条件の側にだけあり、読み手のコードは変えない。上端と高さが親と違う条件で、ライブの写像と JPEG の写像が 1e-6 ライブ画素以内で一致する事を試験で固定する（ADR-0046）
- **範囲の大きさの変化は、計画ができた時に出す**: 新しい範囲で計画ができた時、幅・高さ・上下右の端の前後を、画面・報告・CLI・ログに出す（4 節、6 節）。計画ができる前に止まった時（帯が取れない `band-uncovered` など）は新しい側の値が無いので、前の値だけを出す（報告の新しい側の欄は null）
- **R1 に残差の検査は足さない**: R1 の p0 は R2 の始めの見当にしか使われず、確定には R2 と確かめの推定が要る。残差の線は新しい閾値になるので、別の課題（#304）で扱う。R2 の前の範囲は p0 で選ぶので、p0 が外れていると R2 は縮めすぎた範囲で回りうる。候補の範囲は R2 の姿勢で選び直すので、確定まで進む道は増えない

## 4. 画面に出す数

`Proposal::display`。確定できない時も、出せる所まで埋める。

- A に対する B の位置の変化（図面の座標の言葉。`OutputFrameOf` を通すので取付が 180° でも向きは逆にならない。左右と上下を分けて出す）と、位置・回り・傾き・高さの大きさ
- 細かい合わせの姿勢が無い断りでは、広く探す段（R1）が決めた A に対する B の位置の変化（左右・上下・回り）を「目安」として出す。R1 は傾きと高さを測らないので、そう書く。R2 の姿勢がある時は、R2 の値の行だけを出す
- 重なりの幅（新しいラスタの全行の最も狭い所、mm）
- 継ぎ目の列と図面の上の位置（新旧）、ラスタの大きさ（新旧）。ラスタの大きさの行に、幅・高さの前後と、右端が動いた量、上端と下端が動いた量を出す。上下が縮む時は「図面の下（または上）の約 N mm は合成に入りません」と書く
- 範囲の上か下の行を B が写していない時（`band-uncovered`）は、写していない行の数と mm を、上と下に分けて出す。数える行は、A と B の両方に写る所が無い行で、端から内へ、最初に写る行まで数える
- 継ぎ目が写真の端からどれだけの所か（A の右端と B の左端への距離。画素と幅に対する割合）。校正が確かな範囲の外へ寄ると、レンズの外挿が効いて誤差が出やすい（`rig-profile-v2.md`）ので、校正の画面に必ず出す
- 推定の質: B の画素での当てはめの残差（`ProfileFit`）、確かめの推定が残したずれ

## 5. 確定させない線

新しい閾値は作らない。線はすべて条件の欄か、推定器の既存の判定。確定させないとき `Proposal::refusals` に符号が入る（`RefusalCode`）。

1. 重なりが一つに決まり、その位置で出力の範囲が作れる。落ちる所で符号が違う
   - R1 で重なりが一つに決まる（`no-overlap`）。重なりが幅の 10 % を割るほど広げた組はここで落ちる。`no-overlap` は R1 が重なりを見つけられなかった時だけに使い、所見の理由に R1 の理由を入れる
   - 範囲の上か下の行を B が写していない、または A と B の両方に写る列が全行に共通しない（`band-uncovered`）。R1 が重なりを見つけた後の断り。カメラが上下にずれた、または回った組で出る
   - 範囲の幅が無くなる（`range-collapsed`）
2. R2 が `verified`（`estimate-not-verified`。理由は推定の `reasons`）
3. 確かめの推定が `verified` で、継ぎ目の列の上で適用するずれ（姿勢と、紙面を推定した時はその平面）が `registration.limits.convergencePx` 以下（`reestimate-not-verified`、`reestimate-displacement`）。焼き込んだ profile を製品と同じ経路でもう一度推定して、ほぼ 0 になる事を実行時に確かめる。R2 の始めを大きな p_b で回す経路の取り違えもここで捕まる
4. R2 の傾き |(rx, ry)| が `registration.envelope.tiltDeg` 以下、高さ |tz| が `heightPercent` 以下（`tilt-exceeded`、`height-exceeded`）。超えるのは「動かした」でなく「向きや高さが変わった」で、チャートでの校正が要る
5. 作る時の検査 (a)〜(d)（`creation-check-failed`。検査の文は `detail` に入る）
6. 出力ラスタが描画の限界以下（`raster-too-large`）で、profile の用紙の内側（`raster-outside-sheet`）
7. 位置の計算が成り立つ（`estimate-failed`）。推定器が設定を断った、または例外を返した時
8. 新しい profile と記録が読み手を通る（`profile-invalid`）
9. 呼び手の中止の合図（`stopped`）。R1 と作る時の検査は合図を見ないので、待ちが数十秒になる事がある。合図には利用者の中止だけをつなぐ（期限をつなぐと `stopped` と誤って出る）

### 断りの下位の理由

符号の下に、閉じた集合の下位の理由を持つものがある。所見の `reason` と報告に入る（文やパスは入らない）。

| 符号 | どこで | 下位の理由 | 報告に出す数 |
|---|---|---|---|
| `no-overlap` | R1 が決まらない | R1 の理由: `prior-rejected`・`no-tiles`・`insufficient-tiles`・`outside-image`・`tied-starts`・`no-correspondence`・`fit-failed` | `wideSearch`（合意したタイルと対応の数） |
| `band-uncovered` | 範囲に B が写らない行がある、または範囲に共通の列が無い。始めの姿勢 p0 と、R2 の姿勢 p-hat のどちらでも出る | `top`・`bottom`・`top-and-bottom`（その端の行を B が写していない）、`all-rows`（どの行にも写っていない）、`no-common-column`（どの行にも重なりはあるが、上から下まで共通の列が無い） | `display.targetCoverShortfall`（どちらの姿勢か、上と下の行数と mm） |
| `range-collapsed` | 範囲の右端が左端を越える | `no-width` | 新しい側の値は出さない（`display.widthNewPx` は null） |

推定器の理由にも、同じ文字列の `no-overlap` がある（`content_registration` の理由。報告 v8 の書式に入っているので変えない）。画面の文は符号で先に分けるので、2 つは混ざらない。

### 確かめられなかった時の扱い（所有者の決定）

上の符号は、呼び手（`recalibration_job.hpp`）が三つに分ける。「確かめられなかった」は、目印が足りなくて測れなかっただけで、合っていない印が何も見つかっていない時に限る。合っていないと測れた校正、合っていない疑いの印が 1 つでもある校正は確定させない。

| 区分 | 符号 | 扱い |
|---|---|---|
| 何も作れなかった | `no-overlap`、`band-uncovered`、`range-collapsed`、`estimate-failed`、`estimate-not-verified`、`stopped` | 確定させない |
| 確かめて合っていなかった・疑いがある | `tilt-exceeded`、`height-exceeded`、`creation-check-failed`、`raster-too-large`、`raster-outside-sheet`、`profile-invalid`、`reestimate-displacement`、`reestimate-not-verified`（確かめの推定が範囲の外と出た時）、`reestimate-doubtful`（確かめの推定が `undetermined` で、理由に「目印が足りない」の組の外が 1 つでもある時）、見本の推定が範囲の外（`sample-estimate-out-of-envelope`）、見本の推定が `undetermined` で理由に組の外がある時（`sample-estimate-doubtful`）、見本のゲートが `fail` で原因が `lift`・`pose`・`displacement`（`gate-fail`）、ゲートの `transition-outside-band`（`gate-transition-outside-band`）、ゲートの知らない符号と、状態が `pass` でないのに符号が無い時、知らない状態（`gate-unknown`）、ゲートの `gate-undetermined`（継ぎ目のずれを測る設定の食い違い。確かめる仕組みの故障で、目印の量の話ではない。文は「技術担当へ知らせてください」）、見本のゲートが `not_run`（`gate-not-run`。時間が足りなかった時も、処理が止まった時も確定させない。理由は finding の reason に入り、文だけが変わる。時間切れは「撮り直す」を押して撮り直す案内（続けて起きる時は技術担当へ）、処理の停止は技術担当への案内） | 確定させない |
| 確かめられなかった | `reestimate-not-verified`（確かめの推定が `undetermined` で、理由のすべてが「目印が足りない」の組）、見本の推定が `undetermined` で理由のすべてが同じ組（`sample-estimate-undetermined`）、見本のゲートの `nothing-measured`・`content-unmeasured`・`dx-unmeasured`・`placement-unverified`（符号ごとに `gate-nothing-measured` などの文） | 既定は、警告を見たうえで人が確定できる。定数 `kRecalibrationUnverifiedPolicy` で確定させない側にも切り替えられる |
| 測ったら怪しかった（所有者の答え待ち） | 見本のゲートの `unconfirmed-content`（基準を超えた点が測り直しで確かめられなかった）、`one-sided-content`（片方のカメラにだけ写る所がある） | 既定は確定させない（`gate-unconfirmed-content`、`gate-one-sided-content`）。定数 `kRecalibrationSuspectContentPolicy` を `allow_with_warning` にすると「確かめられなかった」と同じく警告つきで確定できる |

警告つきで確定できる区分に入るのは、これまでどおり「確かめの推定が目印の不足だけで測れなかった」時（`reestimate-not-verified` が 1 つだけ）に限る。`band-uncovered` と `range-collapsed` は幾何の断りで、目印の量には依らず、候補ができる前に止まるので、この区分には入らない。範囲を超えた結果を丸めて合格にしない事も変わらない。

推定（確かめの推定と見本の推定）の「目印が足りない」の組は、`content_registration::AssessEvidenceShortage` が 1 か所で決める。確かめの推定、見本の推定、画面の文がこの関数だけを通る。理由は複数並ぶので、全部がこの組に入る時だけ「確かめられなかった」で、1 つでも外があれば疑いとして確定させない。理由が空の `undetermined` と、知らない符号も疑い。`unique-blocks` は推定器の 2 か所（粗い段と V2）から同じ符号で出る。`too-few-points` は細かい段で点が足りずに止まった符号で、この時は V2 が走らない。どちらも粗い段の数（一意の塊・一致した塊・目印の塊・一致した目印の塊・票で勝った位置と別の位置を指した目印の有無）で分け、数は推定のメモリ上の診断から渡す。別の位置を指した目印の数は、渡されなければ疑いになる値を持つ。v8 の報告は目印と票の数を持たないので、読み戻した記録では分けない。

| 区分 | 理由の符号 |
|---|---|
| 目印が足りない | `coarse-no-unique-blocks`、`repeating-only`、`too-few-points`（粗い段が何も数えていない時。数えた時は、その数が V2 を通る形か、下の `unique-blocks` の 2 つ目と同じく目印の数だけで落ちる形の時だけ）、`prediction-uncertain`、`too-dark`、`unique-blocks`（粗い段が塊の数で止まった時＝目印の塊が 1 以上、一意の塊が最小数未満で、一致の数がまだ数えられていない時。または V2 が目印の数だけで落ちた時＝目印の塊が 1 以上・最小数未満で、その全部が当てはめと一致し、一致した塊が最小数以上かつ使った塊の半分以上の時。どちらも、票で勝った位置と別の位置を指した目印が 1 つも無い時に限る） |
| 合っていない疑い | `coarse-ambiguous`、`coarse-inconsistent`、`fit-failed`、`not-converged`、`residual-shape`、`starts-disagree`、`no-overlap`、`estimate-failed`、`displacement-failed`、`time-budget`、`brown-lowe`（測った点が全部合っていても V1 を通らない数＝`points·(1−β) ≤ α` で、かつ `0 < inliers ≤ points` の時だけは目印が足りない側。点の数だけで落ちている時に限る。α・β は条件の `registration.limits` の値で新しい閾値ではない。α が有限で 0 以上、β が有限で 0 以上 1 未満でない時、`points` が 0 の時、`inliers` が 0 の時、`inliers` が `points` を超える時は疑い。今の値 α8・β0.3、点の最小数 12 では `points·(1−β)` は 8.4 以上なので起きず、`brown-lowe` は常に疑いになる）、`unique-blocks`（上の 2 つ以外。票で勝った位置と別の位置を指した目印が 1 つでもある時（粗い段が止まった時も、V2 で落ちた時も）、一意の塊の半分を超える数が当てはめと食い違った時、最小数以上あった目印が除かれて最小数を割った時、目印が 1 つでも除かれた時、目印の塊が 0 の時、数が欠けている・食い違う時、塊の最小数が設定されていない時。位置だけの推定では数えた塊はすべて目印なので、V2 から出る `unique-blocks` は常に疑い）、`too-few-points`（粗い段が数えた時で、上の場合以外。使った塊の半分を超える数が当てはめと食い違った時、目印が除かれて一致した目印が最小数を割った時、最小数未満の目印のうち 1 つでも除かれたか別の位置を指した時、目印の塊が 0 の時、数が食い違う時、塊の最小数が設定されていない時）、知らない符号 |

上の表で `too-few-points` が「目印が足りない」に入るのは、さらに次を両方満たす時だけ。細かい段が 1 回目の測りで止まった（繰り返しの回数が 1）。粗い段が何も数えていない時も、票で勝った位置と別の位置を指した目印が無い。2 回目以降の点不足は、前の回で最小数以上を測って当てはめた後に崩れた形で、目印の量の話ではないので疑いにする。繰り返しの回数や、別の位置を指した目印の数が渡されなければ疑い。細かい段の早い戻り、繰り返しの回数、2 つ目の始点の扱い、V1 の α・β、点の最小数を変える時は、この分け方も同じ commit で見直し、セキュリティの確かめを通す。

見本のゲートは状態でなく、ゲートの `gate_findings` の符号で分ける（`ClassifyGateFinding`）。状態が `fail` で原因が `unmeasurable` の時と `undetermined` の時が対象で、符号が複数あれば 1 つずつ分け、1 つでも確定させない符号があれば確定させない。基準を超えた（`lift`・`pose`・`displacement`）時は符号を見ずに `gate-fail`。

画面の継ぎ目のずれの行は、測れた値（最大・基準・測れた行の割合）だけを書き、確かめられたかどうかは書かない。それは findings の文が言う。見本の推定だけが疑いでゲートが `pass` の時は、`sample-estimate-doubtful` の文が「継ぎ目のずれが基準内でも、この校正は使えません」と添える。α・β・点の最小数・塊の最小数は開発用の仮の値で、値が変われば「目印が足りない」に入る組が出る（式はコードに残してある）。

確かめられないまま確定した改訂は、条件 v3 の書式に印を置く場所が無いので、校正の報告（`recalibration-report.json`）と確定の記録（`confirmation.json`）とログに残る。画面は「未確認の校正」と出す。見本のゲート（GΩ）は確かめの独立した守りなので、結果（測れたか、ずれの値と基準、測れた行の割合）を必ず画面と報告に並べる。

### 範囲の外に出た手直しから始める

有効な改訂の手直し（`manual-adjustment`）の基準の姿勢が範囲の外に出ていると、読み手は `pose_outside_envelope` で断り、「rollback するか、校正をやり直してください」と案内する。校正のやり直しはこの状態からも始められる。呼び手は、改訂の列を範囲を見ずに読み直し（`LoadActiveFixedCompositeRevisionV3`。列・profile・単一の出どころは範囲を見る前に検査済み）、有効な改訂を親にする。出力ラスタの決め方と「位置の変化」の基準は、親の基準の姿勢でなく profile の姿勢（0）にする（`Display::previous_outside_envelope` が立ち、画面に「前の手直しは範囲の外だったため、校正の位置からの変化を出します」と出る）。確定した `recalibrated` は基準の姿勢が 0 なので範囲の内になる。列が壊れている・profile が無い・違う・v1/v2 が並ぶ時は、これまでどおり断る。

継ぎ目のずれのゲートによる確かめ（GΩ）は見本の合成の側（呼び手）で行う。計算の側の確かめ（`VerifyCandidate`）は同じ組での焼き込みの確かめで、精度の独立な確かめではない。

## 6. 記録

- 推定の記録 `a0.pair-recalibration-estimate.v1`（`Proposal::estimate_record_text`）: 撮影の組の識別（`pairId`・`measuredAt`）、基準と対象のカメラ、組の 2 枚の原画像の SHA-256、親の改訂・profile の SHA-256 と fingerprint と `provenanceId` と `toolId`（`reanchoredBefore` は親がすでに取り直した物か）、R1 の結果、R2 の結果（姿勢・各成分の標準偏差・事前分布の標準偏差・最後の当てはめの条件数・点と inlier の数・対象のカメラの画素での残差 `estimate.targetResidualPx`）。パスを持たない。改訂の `reportSha256` はこの記録の SHA-256
- 新しい profile の `provenanceId` は `pair-reanchor-` ＋ この記録の SHA-256 の先頭 16 桁
- 確かめの結果、表示の数は `Proposal` に持つだけで記録のハッシュには入れない（記録を指す profile と循環しないため）。呼び手の校正の報告に載せる
- 推定の記録は #439 では変えない。そのハッシュは条件の `reportSha256` と profile の `provenanceId` に入るので、変えると左右だけ動かした組の候補のバイト列まで変わる

### カメラを書く欄

記録 3 種（推定の記録、校正の報告 `a0.pair-recalibration-report.v1`、確定の記録 `a0.pair-recalibration-confirmation.v1`）は、同じ形でカメラを書く（ADR-0045 の決定 4）。

- `referenceCamera`（基準のカメラ。この校正で動かさない側）と `targetCamera`（対象のカメラ。写像を取り直す側）を、`pairId` の直後（推定の記録は `measuredAt` の直後）に書く。値は alias で、この校正では `CAM-A` と `CAM-B`。値は `fixed_composite_recalibration.hpp` の定数 `kReferenceCamera`・`kTargetCamera` からだけ書き、書き手に alias を直書きしない
- カメラごとの値は alias を鍵にしたオブジェクトで、鍵は役の順ではなく alias の順（`CAM-A`、`CAM-B`）に並べる。今の 2 台では基準の `CAM-A` が先になる（`fixed_composite_recalibration.hpp` の `static_assert` が、基準の alias が対象の alias より前である事を確かめる）。該当する欄は、推定の記録と校正の報告の `originalSha256`（組の 2 枚の原画像の SHA-256）と、校正の報告の `display.edgeShare`（継ぎ目から基準の右端・対象の左端までの距離の、写真の幅に対する割合）
- `originalSha256` の値: 推定の記録は 2 枚とも原画像と照らした後に作るので、原画像の SHA-256 が入る。校正の報告は、呼び手が渡したハッシュか、呼び手が渡さなかった側を原画像から取ったハッシュが入り、原画像と照らした値とは限らない。原画像を読めずに止まった時（`decode-failed`）は原画像と照らしていない値が、照合が合わなかった時（`hash-mismatch`）は照らして合わなかった値が入りうる。呼び手がハッシュを渡さず、その側の原画像を読む前に止まった時は空の文字列（`tests/recalibration_job_tests.cpp` の `hash-mismatch` の試験が、CAM-A に渡した値、CAM-B に空の文字列が入る事を固定する）
- 対象のカメラだけの値は名前を役で始める（`estimate.targetResidualPx`）。欄の名前に A・B の記号を埋めない
- 基準の姿勢に対する対象の姿勢など、2 台の関係を表す値（`wideSearch`・`estimate.pose`・`display.motion*` など）は、役の欄のとおり基準 `CAM-A` に対する対象 `CAM-B` の値
- 記録の文字列は位置合わせの値（B の写像・出力のラスタ・継ぎ目の列・基準の姿勢）を作る計算に入らない。入るのは推定の記録の SHA-256 だけで、それを通して改訂の `reportSha256`、新しい profile の `provenanceId`、その profile のファイル名と SHA-256・fingerprint、改訂の SHA-256 が変わる。記録の書き方を変えると、新しく作る校正のこれらのハッシュの値は変わるが、ライブの合成にも保存する JPEG の合成にも影響しない

### 版の決まり

3 種の記録の版は v1 のままで、公開の main に入った後に、欄を足す・除く、欄の名前・型・意味を変える時は新しい版（v2）にする。#439 の欄は、記録が公開の main に入る前に足したので、v1 のまま足した。確定の記録の読み手（`RecalibrationRecordedAsUnchecked`）は、その時も v1 を読み続ける（起動し直した後の「未確認の校正」の印のため）。公開する前に書かれた記録（option を ON にした開発のビルドで書いた物）は、欄を足す・名前を改める前の形があっても、古い形を読む仕組みを持たない。条件 v3・報告 v8 の決まり（`fixed-composite-registration-formats.md` の 1 節の決まり 8）はこの 3 種には及ばない。

## 7. 書き込む順（呼び手の仕事）

確定の時だけ、設定のフォルダに次の順で書く。計算の時にメモリに持った物を書く（校正用のフォルダに書いた写しを読み戻さない）。

1. 有効な改訂を読み直し、その SHA-256 が `parentSha256` と同じか確かめる
2. profile の写しを書く（`CopyFixedCompositeProfile`。名前は内容の hash）
3. 改訂を書く（`WriteFixedCompositeConditionV3`。排他の `.partial`、読み直し、置き換えなしの改名）
4. 読み直して、有効な改訂の SHA-256 が候補と同じか確かめる

2 の後で 3 が失敗すると profile の写しだけが残る。名前が内容なので害はなく、有効な改訂は前のまま。

## 8. 読み手への影響

`recalibrated` を知らない読み手（#434 より前）は改訂の列全体を拒否する。C を描かず、撮影は原画像だけを残し、合成しない。前の改訂へは倒れない。後から `values` や `rollback` を足しても古い読み手は読めないままなので、校正をやり直した後は新しい版のアプリだけを使う。

## 9. 限界と未検証

- 間隔を広げると、重なりが約 1 mm ごとに 1 mm 減る。必要な重なりは範囲の項（位置・回転・高さ・傾き・紙面・浮き）と混ぜ幅で決まり、作る時の検査が判定する。広げるほど厚い冊子の視差は間隔に比例して大きくなる
- 帯は縦に細長いので、基線の向きの平行移動 tx、高さ tz、縦軸まわりの傾き ry は帯の中でほぼ区別できない。推定器はこれを承知して、見えない向きを弱い事前分布で p_b（ここでは p0。tx, ty, rz だけ）へ引く。B が平行に動いた前提が崩れた時の台形のゆがみは継ぎ目から遠い所に残り、継ぎ目のゲートは見ない。5 節の 3 と 4 が実行時の守りで、継ぎ目から遠い所の寸法は実機で定規などを置いて確かめる
- 取り直しを重ねても、見える向きは毎回図面から決め直し、見えない向きは p0 に留まるので誤差は積み上がらない（※推定）
- A を動かした時（向きが変わった時）は、この流れでは気づけない。A を付け直した組で、1 組で正しく合わせ直せるのは、A の傾きと高さが範囲の内に戻っていて、A の面内のずれ（図面が出力の中で動く）を受け入れる時に限る。向きが範囲を超えた時は `tilt-exceeded` などで断り、チャートでの校正が要る（A の向きを 1 組から作り直す事はしない。1 組からでは、A が傾いたのか B が傾いたのかを区別できない）
- カメラが上下にずれた時は、範囲の高さが縮む（3.2）。縮んだ分は合成に入らないので、画面と報告の数で確かめる。縮められない（B が写る行が残らない、継ぎ目の列が上から下まで写らない）時は、向きと量を出して断る。削る量は B の写る端が継ぎ目の列で動いた分までで、回りで動いた分も含む。右端は B の右の辺で決めるので、回りでは残した行の端で右の辺が引っ込んだ分だけ幅が狭まる（量は画面と報告に出る）
- 上下に少しだけずれた組で、門 1 は通って削らないが、作る時の検査が範囲の頂点を数えて断る帯がある（合成の組では上へ 5.5〜6.0 mm。それより少なければ削らずに通り、多ければ削って通る）。断る時の案内（カメラを元に近づける）で通る。直す案は別の課題（#304）で扱う
- 削ってよい量は継ぎ目の列で測る。B が回って、範囲の右の端で B の下の辺が継ぎ目より多く上がる（上の辺が多く下がる）と、右下（右上）の角を B が写さず、作る時の検査が断る
- 画面の「位置の変化」の上下の量は B の視野の中心での平行移動で、縮んだ量は継ぎ目の列で測った B の端の動き（回りの分を含む）なので、少し違う事がある
- 実機の K と公称の K の差が大きな移動でどう効くかは、合成の組では確かめた範囲だけ（試験の欄）。実機は未検証
