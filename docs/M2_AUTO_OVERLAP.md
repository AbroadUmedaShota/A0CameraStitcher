## 0. 要約

- 今の自動位置合わせは、粗い一段の探索で最上位の 1 候補だけを残し、曖昧さを測らずに適用する。机の格子・床・画像端の明るさの傾きのような低い周波数の模様に引っ張られると、外れた候補をそのまま出す（3 節）
- 推す案は、OpenCV を使わない自前の推定器（勾配で比べる多段探索、候補を複数残す、重なり帯をタイルに分けて検証し、合議で相似を当てはめる）。ライブでは概略を、撮影 JPEG では同じ推定器で精密に求める（5 節の案 A＋C）
- 見つける時は、起動時に 1 回、ボタン、撮影の後。frame ごとの推定はしない（6 節）
- 見つけた相似は「保持値」として開発経路の中だけで持ち、rig profile には書かない。製品経路（承認 profile）で撮影をまたいで保持するなら ADR の改定が要る。草案の要点を 6.4 節に置き、判断は R4 の実測の後にする
- 明るさの差は、照明が原因ではない前提で、露出の設定・カメラ個体差・周辺減光・見る角度による反射の 4 つに分けて切り分ける。重なり帯の全体を同じ白い紙で覆って両台で 1 回撮れば、照明と紙のむらが打ち消され、全体のゲインと周辺減光を分けて見られる（9 節）
- 二台の小さな相対回転（今回は約 1°）は、ADR-0021 と同じ 3 段（目標・自動補正上限・超過）で扱う。上限の内側ならライブの C と撮影 JPEG の合成の両方で自動で補正し、超えたら補正せずに警告して、何度・どちら回りに直すかを案内する。上限の値と、撮影を止めるか警告だけにするかは所有者が決める。台形（傾き）は相似では直らないので、自動補正せず警告に寄せる（8.3・8.4 節）

## 1. 目的と範囲

二台の重なりをアプリが自動で見つけ、ライブの C と撮影 JPEG の未校正 Merge を合わせる。カメラ間の距離や高さが変わっても、操作者が数値を合わせ直さずに済むようにする。所有者の「撮影 → ずれの確認 → 調整 → 再撮影」の流れに、ずれの量と調整の方向を数値で出して組み込む。

範囲:

- 開発経路（未校正の C、未校正 Merge、StillReview）での重なりの自動検出、相似（平行移動・回転・等方倍率）の推定と適用
- 推定のタイミング、結果の保持、撮影 JPEG への引き継ぎ
- 明るさ・色の差の切り分けと、全体のゲイン・オフセットの自動補正
- 失敗・信用できない時の状態と表示（#360 の状態に揃える）
- 製品経路（承認 profile）との関係、必要な ADR の改定の要点

範囲外:

- 判定のしきい値の決定、最終 rig の承認（#43）、校正 profile の発行（#45）
- 自由な homography、レンズ歪み・台形の推定（校正 R4 の役目）
- 二台の相対的な向き（0/90/180/270°・鏡像）の自動判定（#360 の設計草案 15 節のとおり人が選ぶ）
- カメラの設定の書き込み（露出・周辺光量補正など。アプリは書かない決まり）
- 出力全体の実寸（DPI）の保証。相対の位置合わせでは見えない（4 節）

## 3. 今の自動位置合わせが外れる原因の見立て

参考値（#360・#362 で記録した吊り下げリグの実測）: 同じ設置（`rotated-180`）で、1 回目は重なり 106 画素・上下 77 画素・相関 0.57、別の回は重なり 318 画素・上下 13 画素・相関 0.896。撮影 JPEG では、重なりは幅の約半分だった（目視）。

### 3.1 実測との突き合わせ

- 318 画素 × 11.5（7360/640）≈ 3,660 画素（換算値、幅の約半分）。正しい回の値は、撮影 JPEG で重なりが幅の約半分だった目視と合う
- 106 画素（幅の約 17%）は小さい重なりの側の候補で、上下 77 画素も大きい。外れた回は、別の場所の山を拾ったと読める
- 相対回転 1° は、ライブ（640×427 画素と仮定）で上端と下端の横のずれの差が約 7.5 画素、JPEG で約 86 画素。平行移動だけで最も良く合わせると上下の端に ±43 画素ほど残り、目視の二重写り 25〜50 画素と合う（※推定。歪み・台形の分も混じる）

## 4. 前提の整理: 二つの経路と、距離の変化の見え方

### 4.1 二つの経路

| 経路 | 今あるもの | 幾何の基準 | 本書での扱い |
|---|---|---|---|
| 開発経路（未校正） | 開発用の C、未校正 Merge、StillReview | 基準が無い。C の重なり・上下（と #361 の向き）だけ | #362 の実装の主な対象。相似の推定と保持値をここに入れる |
| 製品経路（承認 profile） | ADR-0034 の profile v2、撮影ごとの上限つき補正（#316〜#325）、ADR-0036 の製品 C（Proposed） | 承認 profile の固定写像 | 同じ推定器を、撮影ごとの補正の初期値と、上限を超えた時の原因の手がかりに使う。撮影をまたいだ保持は ADR の改定が要る（6.4 節） |

### 4.2 距離が変わった時に何が変わるか

#360 の設計草案 3 節のとおり、リグ全体の高さが変わると、A と B の相対関係では倍率ではなく基線方向の平行移動（重なり幅の変化）として出る。相対の倍率に出るのは、A と B の高さの差とピント送りの差だけ。

- 「距離が変わっても追従する」は、相対の位置合わせでは主に重なり幅（と上下）の追従になる。探索の横の範囲は広いまま残す
- 出力全体の実寸（DPI）・向き・用紙端の欠けは相対の位置合わせでは見えない。距離が変わると実寸がずれるが、本書では保証しない。気づくには用紙の外形か校正が要る（#360 の設計草案 D8）
- 高さが変わると MF のピントがずれる。ぼけると照合が弱くなるので、案内に「ピントの確認」を入れる

## 5. 見つけ方の候補と比較

### 5.1 候補

| 案 | 中身 |
|---|---|
| A 自前の推定器（改良した相関＋タイル検証） | 勾配の強さ（またはエッジ）の画像を平均で縮小した多段で探す。各段で上位 K 候補を残し（近い候補はまとめる）、細かい段へ持ち込む。最上位の候補で重なり帯をタイルに分け、タイルごとに小さく探して局所のずれを測る。タイルのずれから相似を合議で当てはめる（2 タイルの組を全部試し、一致するタイルが最も多い組を選び、一致したタイルで最小二乗。乱数を使わない）。OpenCV は使わない |
| B 特徴点（ORB・AKAZE 等）＋ RANSAC で相似 | OpenCV の特徴点と記述子で対応を取り、RANSAC で 4 自由度の相似を求める |
| C 撮影 JPEG で求めてライブへ縮めて当てる | 撮影の後に JPEG（約 11.5 倍の解像度）で相似を求め、その値を縮小比で C に当てる。見つけ方そのものは A か B を使う |
| D 既存の M2 照合（#318〜#323）をそのまま使う | 固定写像に沿った seed の照合と相似の当てはめ。未校正では固定写像の代わりに名目の写像（恒等＋平行移動の初期値）を作って渡す |

|---|---|---|---|---|
| 開発速度 | 中。相関・構造テンソル・往復照合・端数の詰めは M2 にある部品を共有できる。合議の当てはめは新規だが小さい（※推定） | 速い（呼ぶだけ）。ただし製品経路に入れる手続き（HG-0005、リンク隔離の変更、配布物の追加）が別にかかる | A か B に乗る。撮影の経路と報告の形式の変更が要る | 遅い。未校正の名目写像を作る、全 seed 必須を外れ値に耐える形に変える、の 2 つが要り、承認 profile 用の厳格な契約を崩す恐れがある |
| 運用コスト | 依存が増えない。決定的で、同じ入力に同じ結果 | DLL の配布・版の追跡・供給網の監査が増える。RANSAC は乱数の種を固定しないと結果が揺れる | 撮影するまでライブは概略のまま | 依存は増えない |
| スケーラビリティ（距離・回転の変化への強さ） | 平行移動は広く探せる。回転はタイルの探索半径で決まる範囲まで（小さいタイルなら数度、※推定）。大きな回転は不得手 | 回転・倍率に強い。反復模様（文字・格子）で外れ対応が増え、RANSAC 頼みになる | 精度は最も高い（JPEG で端数画素、※推定）。追従は撮影ごと | seed の探索半径（最大 32 段）の中だけ。大きなずれは不成立 |
| 学習コスト | 低い。今のコードと M2 の部品の延長 | 中。OpenCV の挙動とパラメータ | 低い | 中。厳格な契約の理解が要る |
| 既存スタックとの親和性 | 高い。pure C++・STL・既存 renderer だけ | 低い。#310 の「製品に入れない」決定と衝突する | 高い。所有者の「撮影 → 確認 → 調整」と合う | 製品経路では高い。開発経路では無理がある |

### 5.3 推奨: 案 A を推定器にし、案 C の流れで使う

- ライブ: ボタン（と起動時の 1 回）で案 A を縮小画像に当て、平行移動と概略の回転・倍率を出す。調整中の手早い確認に使う
- 撮影の後: 同じ推定器を JPEG の縮小段と原寸のタイルに当て、ライブの値を初期値にして狭く探す。この値を未校正 Merge に使い、ずれの案内（8 節）に出す
- 製品経路: 承認 profile ができたら、撮影ごとの補正は今の M2 照合（案 D の部品、#318〜#323 → #316）で行う。案 A の推定器は、その初期値と「探索の範囲を超えるずれ」の手がかりに使う

理由:

1. 既存スタックとの親和性: OpenCV を製品経路に入れずに済み、#310 の決定を変えない。M2 の照合の部品（相関、構造テンソル、往復照合、端数の詰め）を共有でき、試験の型（人工画像の既知の変換、負の対照、決定性）もそのまま使える
2. 運用コスト: 依存が増えず、乱数を使わないので結果が決定的。同じ frame で結果がぶれる今の問題（X1）を、候補を複数残して検証する作りで直接つぶせる
3. スケーラビリティ: 3 節の原因の多く（X1〜X5・X7）は、勾配で比べる・候補を残す・タイルの合議で机の面に乗るタイルだけを使う、で対処できる。床のように別の深さにある部分はタイルの合議で外れとして落ちる
4. 開発速度: 撮影 JPEG での推定（案 C）が、そのまま所有者の「撮影 → ずれの確認 → 調整 → 再撮影」の数値の出どころになる。ライブの精度を詰め切らなくても流れが回る

案 B を採らない理由: 製品経路への依存の追加が所有者判断で、今の決定（#310）と衝突する。回転・倍率への強さは利点だが、今の実測のずれ（回転 約 1°、相対倍率はほぼ 1 のはず、4.2 節）は案 A の範囲に収まる見込み（※推定）。ただし OpenCV は開発ツールでは使えるので、案 B を開発用の比較の基準（同じ保存ペアで案 A と結果を並べる）として使う道は残す（I3 の検証方法）。

案 D を開発経路に使わない理由: 承認 profile 用の厳格な契約（全 seed 必須、固定写像が前提）を、未校正のために崩すことになる。製品経路では案 D が正しい置き場所なので、二つの照合が並ぶことになるが、相関・構造テンソル・往復照合の関数を共有して重複を抑える（12 節）。

### 5.4 推定器の手順（案 A）

1. 入力を揃える: #361 の向きを当てた A/B。輝度にし、平均で縮小した段を作る（ライブ: 640 幅から 1/2・1/4、JPEG: 1/4・1/8 など。段の数は設計の定数）
2. 勾配の画像を作る: 各段で横・縦の差分から勾配の強さを作る。広い範囲で変わる明るさ（周辺減光・影）の影響を減らす
3. 粗い段で探す: 事前の位置（保持値 G、7 節）があれば、まずその近くだけを探す。無い時、または近くで成立しない時は今と同じ広い範囲（重なり 10〜90%、上下 ±100 画素）を探す
4. 候補を残す: 窓の大きさの偏り（X3）を抑えるため、比べる標本の数に下限を置き、相関は同じ大きさの帯で比べる。上位 K 候補を、近い候補をまとめたうえで残す。最大と次点の差を記録する
5. 細かい段へ: 各候補を次の段で近くだけ探し直す。最後の段で候補ごとに 6 へ進む
6. タイルで検証する: 候補の位置での重なり帯を縦長の格子（例: 2 列 × 6 行。帯の形で変える）に分ける。模様の二次元性（#319 の構造テンソル）が足りないタイルは使わない。各タイルを小さく探し、往復照合（B → A に戻して同じ位置に戻るか）と最大・次点の差を見て、局所のずれを端数まで求める
7. 合議で相似を当てはめる: 使えるタイルの 2 つの組を全部試し、一致するタイルの数が最も多い相似を選ぶ。同数なら残差の小さい方、それも同じなら「一意でない」。一致したタイルで最小二乗をやり直す。一致したタイルの広がり（#316 の広がりの検査）が足りなければ回転・倍率を出さず、平行移動だけを返す。帯が細く倍率が決まりにくい時は、倍率を 1 に固定した 3 自由度に落とし、そう記録する
8. 候補を選ぶ: 一致したタイルの数、残差、最大と次点の差で候補を並べ、上位と次の候補の区別がつかない時は「判定不能」にする
9. 安定性（ライブのみ）: 続く 2〜3 組の frame で同じ結果（同じ整数位置）になった時だけ適用する。回数は所有者決定欄（N5）

出力は、B の画像中心を軸にした相似（`SimilarityReviewGeometry` と同じ約束: x・y は A に対する B の中心の位置、回転は正が時計回り、倍率は倍数）、状態（10 節）、診断（上位候補・最大と次点の差・タイルごとのずれと採否・残差・使った段と範囲）。

### 6.3 「保持して使う」と規則の折り合い（開発経路）

開発経路では、今も C の重なり・上下の値はセッションの中で持ち続け、撮影 JPEG へ引き継いでいる。保持値 G はこれを相似に広げ、出どころと日時を付けたもの。次の線を守れば、ADR-0021 の「rig profile を自動学習・更新しない」とは別物として扱える。

- G は rig profile ではない。profile のファイルに書かず、承認 profile の代わりにしない。profile の発行（#45）の入力にも自動では使わない
- G は frame ごとに変えない。変えるのは 6.2 節の 3 つの時と、操作者の手動調整だけ
- 新しい推定が「成立」の時だけ G を置き換える。それ以外では G を変えない。置き換えの履歴を残し、前の値に戻せる
- 撮影 JPEG の合成は、G を初期値に使うだけで、その撮影の JPEG から推定し直す（7.2 節）。G が古くても合成の結果は JPEG の推定で決まる

開発経路で要る承認は、#333 の調整範囲に回転・倍率を足すこと（今の文書は「初期版の範囲に含まない」）と、起動時の自動実行と、G の保存のしかた（Q2・Q3・Q5）。ADR の改定は要らない見込み（※要確認: 所有者が開発経路の範囲拡大を ADR で扱うと決めた場合は別）。

### 6.4 製品経路で撮影をまたいで保持する場合（ADR 草案の要点）

製品経路では、撮影ごとの補正 T は撮影の後に保存 JPEG から推定し、次の撮影に持ち越さない（ADR-0021、#360 の設計草案 不変条件 4・12）。距離が承認上限の中で変わるなら、毎回の T が吸収する。上限を超えたら `physical-adjustment-required` で、再校正（R4・#45）を案内する。まずはこれで足りるかを R4 の実測で見る。

足りない（毎回の T が上限近くに張り付く、再校正の手間が大きい）と分かった時のための改定案の要点:

- 題: 操作者が確認した相対位置の保持（承認 profile と撮影ごとの補正の間の層）
- 写像: B の実効の写像を `H_B · T_hold · T_capture` にする。`T_hold` は相似だけ
- 設定のしかた: 撮影 JPEG での推定が成立し、操作者が明示して確認した時だけ。自動では変えない
- 上限: `T_hold` 単独の上限と、`T_hold · T_capture` の合計の上限（校正からの総ずれを ADR-0021 の自動補正上限の中に保つ）を、profile の `correctionEnvelope` か別の欄に置く（値は所有者決定）
- 置き場所: profile とは別のファイルで、profile の fingerprint・取り付けの向き・設定した撮影のペアの hash・日時を持つ。profile の期限より長く効かない。profile の変更・再校正・向きの変更で無効
- 製品 C: ADR-0036 決定 1-2 の写像を `H · T_hold` に改める。frame ごとの推定はしない（不変条件 4 は残す）
- 改定する文: ADR-0021 の安全境界に「操作者が確認した相似の保持は、上限と期限つきで認める。自動の学習ではない」を足す。ADR-0036 決定 1-2・不変条件 4 の読み方を合わせる
- 危険: ずれの蓄積を隠す。合計の上限と期限、再校正の案内で抑える

推奨は「改定は R4 の実測の後に判断」（Q12）。今は開発経路で保持値を運用し、そこで得た「どれくらいの頻度・量で動くか」を判断材料にする。

### 7.2 撮影 JPEG の合成への引き継ぎ

今: C の重なり・上下を縮小比で JPEG 画素に直す（平行移動だけ）。

案:

1. 両台撮影の時、今の `pending_geometry` に加えて G（相似）を渡す。中心を軸にした相似なので、JPEG への換算は x・y に縮小比を掛けるだけで、回転・倍率はそのまま（ライブが撮影画像を拡縮と平行移動だけで写し、縦横の比が同じ前提。#309 で未測定、※要確認）
2. 未校正 Merge の前に、JPEG で推定器を回す。G の換算値を中心に、ライブの不確かさの分だけ探す
3. JPEG の推定が成立すれば、その相似で合成する。成立しなければ、今と同じく G の換算値（平行移動だけ、または相似）で合成し、「映像からの引き継ぎ（JPEG で未確認）」と記録・表示する（Q7）
4. 報告に `geometryBasis=auto-still-similarity`（新しい値）、G の換算値、JPEG の推定値、状態、診断の要点、使った方針の hash を足す。今の v1〜v3 は読めるまま残し、品質の三つの false は変えない。版の上げ方（v4 か v3 に値を足すか）は I3 で決める
5. StillReview で、推定値を手動調整の初期値として開ける。手動調整は今の v3 の形のまま別の改訂で保存する

### 7.3 校正 profile（#45・R4）との関係

- G も JPEG の推定値も、profile に書かない。profile の発行の入力にも自動では使わない
- R4 の校正の後は、承認 profile の固定写像が基準になる。推定器は撮影ごとの補正（#46 の経路）の初期値と、ずれが照合の探索範囲を超えた時の手がかりに回る
- 開発経路で集めた推定値の履歴（距離を変えた時の重なり幅の変化、回転のばらつき）は、#360 の設計草案の T1〜T5（目標・上限）を決める参考の材料として、出典つきで所有者に渡す。自動で値にしない
- 校正の時、チャートの向きの印が両台に写るかの確認（#360 の設計草案 R10）に、G の向きと回転の値を照らし合わせられる

## 8. 「撮影 → ずれの確認 → 調整 → 再撮影」の流れ

### 8.1 流れ

1. ライブ: 起動時の推定（またはボタン）で C を合わせる。概略の回転・上下・重なりを C の下に出す
2. 両台撮影: JPEG で推定し、未校正 Merge を作る
3. ずれの確認: 結果の画面に、数値と調整の案内（8.2 節）、前の撮影との比較を出す
4. 調整: 操作者がリグを動かす。動かしている間はボタンでライブの概略の数値を見て、近づいたかを確かめる
5. 再撮影: 2 に戻る。「ここまで合えば調整不要」の目安は所有者決定欄（#360 の設計草案 T1〜T5 と同じ欄を使い、本書で別に作らない）

### 8.2 出す数値と案内

| 数値 | 単位 | 案内（案） | 注意 |
|---|---|---|---|
| 相対回転 | 度（正が時計回り） | 「B の画像は A に対して時計回りに θ° 回っています。B のカメラを光軸まわりに θ° 戻してください」 | 画像の回転と、カメラ本体を上から見た回す向きの対応は、取り付けで決まる。実機で 1 回、少し回して符号を確かめ、設置手順に書く（※要確認） |
| 上下のずれ | 画素（JPEG）と画像の高さの % | 「B は A より下に Y 画素ずれています。B を前後（画像の上下の向き）に動かしてください」 | mm への換算は縮尺が要る（Q14）。縮尺が無い間は画素と % だけ |
| 重なり | 画素と幅の % | 「重なりは幅の P%。前の撮影より Δ 画素増えました（高さが変わった可能性）」 | 重なりの適否は #360 の設計草案 T5 |
| 相対倍率 | % | 「B は A より S% 大きく写っています。B の高さかピントが A と違います」 | 4.2 節のとおり、リグ全体の高さの変化は倍率に出ない |
| 相似の後の残差 | 画素（最大・RMS）、タイルごとの並び | 「相似で合わない残りが R 画素あります。傾き（台形）かレンズの歪みです。校正の前は区別できません」 | 校正前の残差を物理調整で消せるとは案内しない。レンズの歪みは R4 で入る |
| 明るさの差 | %（9 節） | 「A が B より G% 明るく写っています。両台の露出の設定を確認してください」 | アプリは設定を書かない |
| 状態 | 10 節 | 状態ごとの次の操作 | 「合格」とは書かない |

- 前の撮影との比較: セッションの中で直近の数回分を並べ、調整で縮まったかを見せる。前の撮影の値は判定には使わない（#360 の設計草案 不変条件 12）
- 方向の言葉は「合成画面で見た向き」で書く。部屋の向き（左右・前後）への読み替えは、取り付けの向き（#361）と吊り方で決まるので、設置手順の側で一度決める

### 8.3 相対回転: 上限の内側は自動で補正し、超えたら警告する

所有者の要望（#362）: 「向きもある程度影響ない範囲は自動調整されるようにできる？ あまりにものときは警告出して良いと思う」。

ここでの「向き」は、二台の光軸まわりの小さな相対回転（度）を指す。#361 の取り付けの向き（`normal`／`rotated-180` の離散の設定）とは別のもので、取り付けの向きは今までどおり推定しない。

判定は 3 段で、ADR-0021 と `a0_m2_setup` と同じ考え方にする。

| 回転の大きさ | 扱い | ライブの C | 撮影 JPEG の合成 | 状態（10 節） |
|---|---|---|---|---|
| \|θ\| ≤ 目標（N12） | 影響が小さい範囲。補正を当てるかは #360 の設計草案 D5 と同じ判断（推奨は ADR-0021 の `ready` に合わせて当てない） | D5 の結論どおり | D5 の結論どおり | `accepted` |
| 目標 < \|θ\| ≤ 自動補正上限（N13） | 自動で補正する | B を θ だけ戻して描く | 同じ相似で合成する | `accepted-with-correction` |
| \|θ\| > 自動補正上限 | 補正しない。警告を出し、向きの調整を案内する | 回転を当てない（上限の値で切った部分的な補正もしない）。警告の帯を出す | 推定値で合成しない | `rejected`（理由 `rotation-exceeded`） |
| 上限が未設定 | 回転を求めて数値だけ出す。補正しない（Q17） | 平行移動だけ | 平行移動だけ（今と同じ） | `estimated-not-judged` |

- 上限と等しい値は通す。超えた値を丸めない、上限で切らない。超えた項目は全部記録する（#316 と同じ規則）
- 警告の文（案）: 「B の向きが A に対して時計回りに 1.8° ずれています（自動で直せるのは N13° まで）。B のカメラを光軸まわりに 1.8° 戻してください」。回す向きは合成画面で見た向きで出す。カメラ本体を上から見た時の回す向きへの読み替えは、設置手順で一度決める（8.2 節、※要確認）
- 撮影を止めるか、警告だけにするか（Q16）。推奨は「ライブでは警告だけにし、撮影後の JPEG の判定で `rejected` にする」。ライブでの回転の推定は JPEG より一桁ほど粗い（タイルの位置の誤差を 0.5 画素と仮定すると、ライブで約 0.08°、JPEG で約 0.007°。※推定）。このため上限の近くでは、撮影前に正しく止められない。また、画像の測定で撮影可否を決めることは、操作画面仕様の常時禁止（#360 の設計草案 F9）と ADR-0035・0036 の読み方に関わる（#360 の設計草案 D2・案 2）。開発経路で止めるかは所有者が判断し、製品経路では #360 の結論に従う
- どちらを回すか: 補正は B に当て、A を基準にする（#316・#321 と同じ）。案内も B を回す形で出す。リグの構造上 A を回す方が楽なら、符号を逆にした案内に切り替える設定を足す（※要確認）

### 8.4 台形（傾き）は相似では直らない

- 相似（平行移動・回転・等方倍率）では台形を表せない。カメラの前後・左右の傾きで出る台形は、相似を当てはめた後の残差として残る（#360 の設計草案 7.1 節）。自由な homography で直すことは ADR-0021・0036 が禁じているので、自動補正はせず、警告の側に寄せる
- 測り方: タイルごとの、相似を当てはめた後の残差（最大と RMS）と、その並びを診断に出す。並びの例は、重なり帯の上と下で残差の向きが逆になる、上から下へ倍率が少しずつ変わる、など
- 扱い: 残差が所有者の値（N14。製品経路では #360 の設計草案 T4）を超えたら警告する。文（案）は「相似で合わない残りが R 画素あります。カメラの前後・左右の傾き（台形）か、レンズの歪みの可能性があります」。校正前は台形とレンズの歪みを区別できないので、「傾きを直せば消える」とは書かない。校正後（profile に歪みが入った後）は、残差の主な原因は校正後に変わった傾きになり、#360 の `rejected`（`fit-residual-exceeded`）で扱う
- 撮影を止めるかは、回転と同じく Q16 に含める。推奨は警告だけ
- 残差の並びから傾きの向き（どちら側が遠いか）を推して案内に出すかは、#360 の設計草案 K2 と同じく後で判断する。R4 で残差が問題になった時に、補正ではなく診断として足す

## 9. 明るさ・色の差

所有者の確認（#362）: 照明の左右差は無い。カメラ側の問題と思われる。自動で合わせたい。

### 9.1 原因の候補

重なった所は、A と B が同じ時に同じ紙の同じ場所を見ている。このため照明のむらは重なった所の A と B の比には出ない。比に出るのは次の 4 つ。

| # | 原因 | A/B の比への出方 | 補正の置き場所（案） |
|---|---|---|---|
| L1 | 露出の設定の違い（シャッター速度・絞り・ISO・露出補正） | 重なり帯のどこでも同じ比 | まず設定を揃える（人がカメラのメニューで。アプリは書かない）。残りは全体のゲイン |
| L2 | カメラの処理の設定の違い（ピクチャーコントロール、アクティブ D-ライティング、周辺光量補正、ホワイトバランス） | ほぼ同じ比。アクティブ D-ライティングやトーンの違いは明るさの段で比が変わる | 設定を揃える。残りは全体のゲイン・オフセット |
| L3 | 個体差（センサーの感度、レンズの透過、絞りの再現性） | どこでも同じ比 | 全体のゲイン（撮影ごと、または校正で固定） |
| L4 | 周辺減光 | 重なりは A の右端と B の左端で、どちらも画像の端。帯の中で比が位置により変わる。同じ型のレンズでも、帯の A 寄りの端と B 寄りの端で逆向きの傾きになる | 校正 profile（R4）にカメラごとの半径の式を持たせる。全体のゲインだけでは継ぎ目に段差が残る |
| L5 | 見る角度による反射（光沢のある紙・カッティングマットの艶） | 光る場所だけ比が大きく変わる。半径の式に乗らない | アプリでは直さない。マットな紙・照明の角度で避ける |

参考値: 重なった所では A が約 9% 明るく、色の比はほぼ同じ（#362 本文）。帯の位置による明るさの比の変わり方は、#362 のコメントに記録した。ホワイトバランスの違い（L2 の一部）は色の比がほぼ同じなので小さいと読める。8 bit の値で 9% は、トーンを 2.2 乗と仮定すると光の量で約 0.27 段で、露出の 1/3 段の違いと同じ程度（※推定）。L1・L2 の違いがあるかは、まず撮影済みの JPEG の EXIF で確かめられる（9.4 節 E0）。

### 9.2 補正の分け方

| 層 | 中身 | どこで使う | 置き場所 | 規則との関係 |
|---|---|---|---|---|
| P1 全体のゲイン・オフセット | B のチャンネル別のゲイン・オフセット（#321 の型） | ライブの C、未校正 Merge、製品経路の撮影ごとの補正 | ライブはボタン・起動時の推定と一緒に求め、JPEG は撮影ごとに求める | ADR-0021 の撮影ごとの露出・色の補正と同じ形。上限は所有者決定 |
| P2 周辺減光 | カメラごとの半径の式 `1 + v1 r² + v2 r⁴`（8 bit の値の空間での経験式） | 製品経路（承認 profile）。開発経路では方針ファイルで明示した時だけ | 校正 profile。v2 に欄が無いので、ADR-0034 の改定と schema の版上げが要る | カメラ固有の量なので校正で一度決める。撮影ごとに学習しない |
| P3 物理の対処 | 設定を揃える、マットな紙、照明の角度 | 設置の手順 | 設置手順・案内 | アプリはカメラの設定を書かない |

- 順番は幾何が先。幾何が成立した時だけ、同じ重なり帯・同じタイルで明るさを測る（#322 と同じく、幾何で選んだ点を使う）。幾何が成立していない時に明るさだけを合わせない
- 補正は B だけに当て、A を基準のまま残す（#321 の描画と同じ）。原画像は変えない
- ライブの C では、ボタン・起動時の推定で求めた P1 を表示にだけ使う。frame ごとに求め直さない
- 測る場所は「紙らしい明るい画素」に寄せ、線や影の多いタイルは外す。重なり帯の比をタイルごとに並べた「比の並び」を診断に残す。帯の中で比が傾いていれば P2 の疑い、局所的に跳ねれば L5 の疑いと原因の候補に挙げる（状態は変えない）

### 9.3 ライブの C と撮影 JPEG で同じ値を使えるか

| 量 | 同じ値を使えるか | 理由 |
|---|---|---|
| 幾何（相似） | 条件つきで使える | 中心を軸にした相似なら、x・y を縮小比で換算するだけ。ライブが撮影画像を拡縮と平行移動だけで写す前提（#309 で未測定、※要確認） |
| P1 ゲイン・オフセット | 測ってからでないと使えない | ライブの frame は撮影の JPEG と別の処理で作られる。露出の表示の扱い、トーン、ノイズ低減が違いうる（#353 の文書も「Live と JPEG の明るさ・色の応答の一致は別に検証が要る」としている）。既定はそれぞれで求め、同じ設置で両方を測って差が所有者の許容（N10）に入れば、JPEG の値をライブに当ててよいとする（Q8） |
| P2 周辺減光 | 条件つきで使える | 画像の中心からの相対の半径で式を持てば、縮小に依存しない。ただしライブの frame にカメラの周辺光量補正が当たるかは不明（※要確認） |

### 9.4 切り分けの手順

物理作業は 1 回の実機段にまとめる。先にカメラ不要の 2 つを行い、それで決まれば実機段の中身を減らす。

カメラ不要（物理作業なし）:

- E0 撮影済みの A/B の JPEG の EXIF を比べる（ローカルだけで、公開しない）。シャッター速度・絞り・ISO・露出補正・ホワイトバランス・露出モード。メーカー固有の欄（ピクチャーコントロール、アクティブ D-ライティング、周辺光量補正）が読めるかは※要確認。読めなければ実機段の S1 で人がメニューを見る
- E1 撮影済みの重なり帯で、A/B の比の並びを作る。帯をブロックに分け、紙らしい明るい画素だけの中央値の比を、A の中心からの距離と B の中心からの距離に対して並べる。今の二重写り（25〜50 画素）より十分大きいブロックにすれば、位置ずれの影響は小さい（※推定）。比が帯の中で一定なら L1〜L3、傾いていれば L4 の疑い

実機段（1 回。撮影は今の「両台撮影」の経路で 2 組。対象・回数・中止の条件は事前に所有者が承認する）:

| 順 | 物理の作業 | 記録すること | 分かること |
|---|---|---|---|
| S1 | 両台のカメラのメニューを人が見る。露出モード、シャッター速度、絞り、ISO、露出補正、ホワイトバランス、ピクチャーコントロール、アクティブ D-ライティング、周辺光量補正、自動ゆがみ補正 | 両台の値の表（ローカル） | L1・L2 の違い。違いがあれば、揃えるかを所有者が決めてから S2 へ（揃える作業は人が行う） |
| S2 | 図面を置いたまま、ライブでボタンを数回押す（回数は事前承認）。続けて両台撮影を 1 組 | 各回の候補・状態（今の推定器の基準値として）、撮影ペア | 幾何（重なり・上下・回転）。S3 の比の計算に使う |
| S3 | カメラ・照明・人の位置を動かさずに、マットな白い紙（光沢の無いもの、継ぎ目が出ない大きさ）で重なり帯の全体を覆う。紙は平らに置き、影が乗らないようにする。両台撮影を 1 組 | 撮影ペア。照明・紙の種類のメモ | 重なり帯の比の並び。紙と照明のむらは比で打ち消される |

解析（カメラ不要、実機段の後）:

| S3 の比の並び | 見立て | 次の一手 |
|---|---|---|
| 帯の中で一定。S1 で設定に違いがある | L1・L2 | 設定を揃えて（人が）撮り直して確かめる。残りは P1 |
| 帯の中で一定。S1 で設定が同じ | L3 | P1 で足りる |
| A 寄りと B 寄りで逆向きに傾く。平均の比は 1 に近い | L4（同じ型のレンズの周辺減光） | P2 を R4 で検討する。P1 だけでは段差が残る |
| 傾きと平均の差の両方 | L4 と L1〜L3 の重なり | P1＋P2。帯の比から、共通の半径の式と全体のゲインを同時に当てはめられる（両台のレンズが同じ式という仮定つき） |
| 局所的に跳ねる | L5 | 紙・照明の角度を変える。アプリでは直さない |

- この方法を、紙を A と B の画面の中央にそれぞれ置いて比べる方法より推す理由: 中央に置く方法は紙を動かすので、2 か所の照明の違いが比に入る。重なり帯を覆う方法は、同じ紙の同じ場所を両台が同時に見るので、照明と紙のむらが比から消える。帯は A の中心寄りから端まで、B の端から中心寄りまでをまたぐので、周辺減光の形も同じ 1 組で見える（重なりが幅の半分ほどある今の設置の場合）
- 物理作業の依頼は、S1〜S3 をまとめて先に出す。撮影の開始と Agent の寿命の制約の中で行えるよう、S2 のボタンの回数は少なく決める

## 10. 結果の状態と表示

#360 の設計草案 6 節の状態を使う。開発経路には承認 profile が無く、上限の欄が無い場合が普通なので、開発経路だけの状態を 1 つ足す。

| 状態コード | 表示名（案） | 条件 | 保持値 G | 未校正 Merge | 表示（案） |
|---|---|---|---|---|---|
| `not-run` | 位置合わせを実行できません | 入力が 2 秒より古い・片側が無い、寸法が違う、向きの設定が無効、方針ファイルが不正 | 変えない | 今と同じ扱い | 理由と「A/B の映像を確認してください」 |
| `undetermined` | 重なりを決められません | 候補が無い、上位の候補の区別がつかない、検証に通るタイルが足りない、連続 frame で結果がそろわない、模様が足りない | 変えない | JPEG の推定がこれなら、G の換算値で合成し「JPEG で未確認」と記録（Q7） | 理由、「前の位置のまま表示しています」、原因の候補（模様の不足・反復模様・重なり不足・向きの設定・大きなずれ） |
| `estimated-not-judged` | 位置を求めました（基準による判定なし） | 推定と検証に通った。上限の欄が無いので、上限の内外は判定していない。開発経路だけの状態 | 平行移動の分を置き換える。回転・倍率は上限が置かれた項目だけ当てる（8.3 節、Q17） | 同じ範囲で合成する | 数値と「要目視確認」。上限が未設定の項目は「上限未設定のため補正していません」。「合格」とは書かない |
| `rejected` | 位置は求めましたが、上限を超えています | 推定と検証に通り、所有者が置いた上限（N6・N13・N14）を超えた | 変えない | 推定値を使わず、G の値で合成する（参考の結果として推定値で合成するかは Q6） | 警告。超えた項目と調整の案内（8.2〜8.4 節）。撮影を止めるかは Q16 |

| `accepted` | 位置を合わせました | 全項目が目標の内側 | 置き換える | 推定値で合成する | 数値。品質は未評価 |

- `rejected` と `accepted*` は上限・目標の欄が置かれた時だけ出る。製品経路では欄が無ければ #360 の設計草案 不変条件 8 のとおり `not-run`。`estimated-not-judged` は製品経路では出さない
- 品質（#47）は `not-evaluated` のまま。状態の名前に「合格」を使わない
- 方針ファイル（信用の判定に使う値、N1〜N5）が無い時は、数値を使わない検査だけで判定する: 同点が無い、探索の端に張り付いていない、往復照合が同じ整数位置に戻る、連続 frame で同じ整数位置になる。これに通った候補だけを `estimated-not-judged` にし、通らなければ `undetermined`。今の「最上位の候補を必ず適用する」振る舞いはやめる（Q9）
- C の見出し（案）: 「位置: 自動（映像から・要目視確認）」「位置: 自動（撮影 JPEG から）」「位置: 手動」「位置: 前回の値（日時）」。今の向きの表示（#361）と並べる
- 開発用の診断（ログと画面の折りたたみ）: 上位の候補と最大・次点の差、タイルごとのずれと採否、相似、残差、使った範囲と段、明るさの比の並び。ログは今の `quality_accepted=0` の書き方を続ける
- 撮影 JPEG の実装（#365）は、回転と倍率をそれぞれの上限（N13・N6 の倍率）と比べる。回転が上限の内側なら回転を当て、倍率は方針ファイルに倍率の上限があり、その内側の時だけ当てる。それ以外は倍率を 1 に固め、回転を保ったまま平行移動だけを当てはめ直して合成する。回転が上限を超えたら、平行移動だけで合成する。状態の名前と報告の欄の対応は `docs/WPD_STILL_REVIEW.md` の判定の表に書く

## 11. 守る不変条件

1. 原画像を変えない（画素・hash）。向きの回転も明るさの補正もメモリの上だけ
2. 自由な homography を推定しない。推定は相似（4 自由度）まで。倍率が決まらない時は 3 自由度か平行移動だけに落とし、その旨を記録する
3. rig profile を学習・更新しない。G は profile に書かず、profile の発行の入力にしない
4. ライブで frame ごとに推定しない。推定は起動時の 1 回・ボタン・撮影の後だけ。変化の検知を採っても、表示と促しだけで自動適用しない
5. `undetermined`・`not-run`・`rejected` の推定で G を変えない
6. 承認されていない数値を既定値にしない。信用の判定値と上限は方針ファイルと profile の欄から読み、無ければ 10 節の扱いにする
7. 撮影 JPEG の合成の幾何は、その JPEG での推定か、記録した引き継ぎ値か、手動調整のどれかで、どれを使ったかを報告に残す
8. 推定は #361 の向きを当てた後の座標で行い、向きを記録する。向きが違う G は使わない。向きを画像から推定しない
9. 同じ入力からは同じ結果を出す。乱数を使わない（使うなら種を固定して記録する）
10. 明るさの推定は幾何が成立した後だけ。補正は B にだけ当て、A を基準のまま残す
11. 補正の成立と品質の合格を分ける。品質は #47 が判定するまで `not-evaluated`
12. アプリからカメラの設定を書かない。案内は人が設定を確かめる形にする
13. 古い入力・片側だけの入力で推定しない（今の 2 秒の規則）
14. 1 回の撮影の判定に前の撮影の結果を使わない。前の値は初期値と比較の表示だけ
15. 出力の実寸・向きの正しさを主張しない（相対の位置合わせでは見えない）
16. 回転・倍率の自動補正は、承認された上限（開発経路は方針ファイル、製品経路は profile）の内側だけで行う。回転と倍率は別々に上限と比べ、上限が無い項目・上限を超えた項目は補正しない（倍率なら 1 のまま）。上限を超えた値を上限で切って部分的に補正しない
17. 台形（傾き）を自動で補正しない。相似の後の残差は警告と診断にだけ使う

## 12. 実装ガイドライン

- 置き場所: 推定器はカメラ・ファイル・時計に依存しない純粋な library にし、`src/m2/experimental` 側に置く（例: `a0/m2/experimental/overlap_estimation.hpp`、名前は案）。ライブ（phase0）と StillReview・未校正 Merge（m2）の両方から使うため。phase0 → m2 の今の依存の向きを保ち、m2 から phase0 を参照しない
- 共有: 相関（平均を引いた正規化相関）、構造テンソル、往復照合、端数の詰めは、M2 の `image_patch_detail.hpp` の実装と関数を共有する形に寄せる。写して二つにしない。共有化の時に #318〜#323 の既存試験と出力が変わらないことを確かめる
- 型: 入力は向きを当てた `BgrImage` 二枚、方針（全引数必須、既定値なし、#318 の `ImagePatchPolicy` と同じ書き方）、事前の位置（任意）。出力は相似・自由度・状態・診断。ライブと JPEG で同じ関数を使い、段の作り方だけを寸法から決める
- 座標の約束: すべて `SimilarityReviewGeometry` と同じ（B の画像中心が軸、x・y は A に対する B の中心、回転は正が時計回り、倍率は倍数）。換算は x・y の縮小比だけにする
- ライブの描画: 今の `RenderPreviewMerge`（平行移動だけ）を、相似を受ける形に広げる。既存 renderer と `SimilarityReviewGeometry` の被覆の切り取りを使う。明るさは #321 の `BgrAffineTransform` を受ける描画の overload を使う
- 並行: 推定は今の合成 worker の中で行い、UI の手動操作の revision が変わったら古い推定を捨てる（今の仕組み）。推定に時間がかかる時もカメラの制御・保存に触れない
- 方針ファイル: カメラ登録と同じローカルのフォルダに置き、#361 の設定ファイルと同じ厳しさで読む（未知・重複の欄、型の誤り、大きさの上限で拒否）。報告に hash を残す
- 履歴ファイル: 追記型、1 行 1 件、行ごとに版を持つ。読み込みは最後の正しい行。書き込みは flush してから次の行
- 試験の入力: 製品の推定器に依存しない独立した生成で、既知の相似・明るさ・周辺減光・机の格子・別の深さの模様（床に見立てて別のずれを持つ帯）・反復文字・無地を作る。生成器にこの推定器が混ざらないことをリンク隔離の検査に足す
- 名前: 状態は kebab-case の英語コード、画面は日本語の表示名で 1 対 1。表示名に「合格」を使わない
- 上限の比較: `AssessSetup` の中の「測定値・目標・自動補正上限」の 3 段の比較を、小さな純粋関数（例: `ClassifyBoundedMetric`、名前は案）に切り出し、`AssessSetup` と開発経路の判定の両方から呼ぶ。切り出しの前後で `m2_setup_assessment_contracts` が同じ結果になることを確かめる。理由コード（`rotation-exceeded`・`scale-exceeded`・`fit-residual-exceeded`）は #316 の文字列をそのまま使い、開発経路の判定にも段の名前を前に付けて並べる（#360 の設計草案 7.7 節）

## 16. 検討して採らなかった案

| 案 | 採らない理由 |
|---|---|
| ライブの frame ごとに推定して C を動かす | ADR-0036 不変条件 4 と #333 の規則に反する。今の推定器でも結果がぶれており、動き続ける C は「ずれの確認」の目安にならない |
| 自由な homography やレンズ歪みを重なりから推定する | ADR-0021・0036 の禁止に当たる。歪みと台形は校正（R4）で持つ |
| 二台の相対的な向き（90°・180°・鏡像）を画像から自動で判定する | #360 の設計草案 15 節のとおり。反復模様で誤った向きを黙って選ぶ恐れがある。向きは #361 の設定で人が選ぶ |
| 探索範囲をさらに広げて外れを減らす | 候補が増えるほど偶然の高い相関を拾う（X7）。広げるのではなく、候補を残して検証する |
| 相関値に合格線を置いて採否を決める（今の相関の値だけで） | 相関は窓の大きさと模様で変わり、0.57 の外れと 0.896 の正解の間に線を引いても別の設置で意味を持たない。最大と次点の差・タイルの合議・往復照合で信用を決める |
| 推定値を rig profile の値として保存する | ADR-0021 の自動学習の禁止に当たる。profile の発行は #45 の校正で行う |
| 照明の補正（位置で変わる明るさ）を重なり帯から推定して全画面に当てる | 照明のむらは重なり帯の A/B 比に出ない（同じ場所を見る）。全画面に当てる根拠が無い。所有者の確認でも照明の左右差は無い |
| アプリがカメラの露出・周辺光量補正の設定を揃える | 設定を書き込まない決まり。人がメニューで揃える |
| 紙を A と B の画面中央にそれぞれ置いて明るさを比べるだけの切り分け | 紙を動かすので 2 か所の照明の違いが比に入る。重なり帯を覆う方法なら照明と紙のむらが打ち消され、周辺減光の形も同じ 1 組で見える（9.4 節）。中央の比較は補助として足してよい |
| 上限を超えた回転を、上限の値まで部分的に補正する | 超えた値を上限で切って通すことになり、#316 と ADR-0021 の「clamp しない」に反する。半分だけ直った継ぎ目は、ずれの確認の目安にもならない |
| 台形を射影変換で自動補正する | ADR-0021・0036 の自由な homography の禁止に当たる。校正前は台形とレンズの歪みを区別できず、直す対象を誤る |
| 開発経路でも #316 の関数をそのまま呼ぶ（名目の写像を作って） | 未校正の値に文書 mm の座標を名乗らせ、校正済みと取り違える恐れがある。規則と理由コードを揃えれば足りる |

## 17. ※要確認の一覧

- ライブの frame の元の画素数と、撮影画像への対応（#309）。縦横の縮小比が同じか
- 机の格子の間隔、撮影距離、床が重なり帯に写る広さ（X5 の確からしさ）
- 3 節の 1 回目と 2 回目の間に、写っていた物（手・影・ピント）に違いがあったか
- 合議に使えるタイルの数が、今の図面と重なり（幅の約半分）で足りるか
- 撮影済み JPEG の EXIF で、メーカー固有の欄（ピクチャーコントロール・アクティブ D-ライティング・周辺光量補正）が読めるか
- ライブの frame にカメラの周辺光量補正が当たるか
- 画像の回転の符号と、カメラ本体を回す向きの対応（取り付けで決まる。実機で 1 回確かめる）
- 開発経路の範囲拡大（Q2・Q3・Q5）を ADR で扱うか、#333 と開発文書の改定で足りるか
- 試験のためのライブ frame の記録が、pilot の間の記録の決定（ADR-0036 の所有者決定 6）の範囲に入るか（Q15）
- 3 節・9 節の実測値を公開リポジトリへ移す時に残すか（ADR-0033 7 節）
- （確認済み）#318〜#323 の関数を共有化する時、既存の報告と出力のバイト列が変わらないか。相関を共有化する前の `f0eabd7` と、共有化の後の main（`b507b73`）で `m2_image_patch_correction_contracts` を Release で作り、evidence（`matching-report.json` と `auto-selection-report.json` の setprecision 17 の JSON 2 つと、JPEG 5 枚）を出して比べた。7 ファイルとも SHA-256 が同じだった
- 相対回転 約 1° は目視からの推定だった。I3（#365）の推定器で記録時の保存ペア 2 組を測っても、どちらも約 1° だった（細かい値は公開しない）。8.3 節の表は 1° の行で読める
- 回転を補正して削れる上下の幅のうち、A0 の全体が収まる余白がどれだけあるか（#42 の DPI と撮影範囲による）
- リグの構造上、回すのは A と B のどちらが楽か（案内の符号の切り替えの要否）
